# Design: Roadmap Agent Output

## Technical Approach

This VS does not add automatic roadmap generation to the CLI. Instead, it standardizes the
expected roadmap output generated by the `roadmap-agent`.

The main artifact is:

```txt
architecture/roadmap.md
```

The roadmap must be designed for two audiences:

1. Humans who need to understand direction and priority.
2. Future Kaddo CLI commands that will create Work Items from roadmap entries.

## Inputs

The `roadmap-agent` should use:

```txt
.kaddo/context-pack.md
architecture/capabilities.md
architecture/current-state.md
architecture/legacy/risks.md
architecture/legacy/unknowns.md
architecture/decision-candidates.md
architecture/knowledge.md
```

Not all files are required. The agent must work with whatever context is available and mark
missing context clearly.

## Output Artifact

The expected output is `architecture/roadmap.md`.

## Roadmap Structure

```txt
# Roadmap

Generated with Kaddo Roadmap Agent.

## Summary
## Assumptions
## Roadmap Principles
## Initiatives

### RM-001: <Initiative Name>
**Goal:**
**Related capabilities:**
**Project area / domain:**
**Impact:** Low / Medium / High
**Risk:** Low / Medium / High
**Suggested Knowledge Level:** K1 / K2 / K3 / K4
**Dependencies:**
**Why this comes now:**
**Candidate Work Items:**
- WI-CANDIDATE-001: <candidate work item>
  - type:
  - suggested knowledge level:
  - expected value:
  - notes:
**Open questions:**
---

## Suggested Execution Order
## Risks and Constraints
## Not Now
## Next Recommended Work Item
```

## Roadmap Entry Requirements

Each roadmap entry should include: clear goal, related capability, impact, risk, dependency,
suggested order, candidate work items and open questions.

## Candidate Work Items

Candidate work items are not actual work items yet. They are roadmap suggestions. A future
command may convert them into real work items:

```txt
kaddo create --from roadmap
```

## Front Matter

Optional front matter may be added for future parsing:

```txt
---
type: roadmap
id: roadmap
status: draft
generated_by: roadmap-agent
knowledge_level: K3
---
```

## Agent Prompt Updates

The `roadmap-agent.md` should explicitly instruct the LLM to:

- not invent business facts,
- reference evidence from context,
- mark assumptions,
- create candidate work items,
- suggest Knowledge Levels,
- separate "Now", "Next" and "Later" if useful,
- keep the roadmap actionable and not aspirational.

## Alternatives Considered

- **Let each user write the roadmap freely** — rejected because future CLI flows need
  structure.
- **Generate roadmap directly from CLI** — rejected because roadmap requires interpretation
  and prioritization, which should happen through LLM + human review.
- **Use only a simple bullet list** — rejected because it would not support a future
  `create --from roadmap`.

## Trade-offs

A structured roadmap is slightly more verbose, but it enables future automation and better
traceability.

## Risks and Mitigation

- Roadmap may feel too formal for small projects → ask for a "minimal actionable roadmap".
- LLM may overproduce initiatives → limit suggested initiatives.
- Generated work items may be too large → prefer small candidate work items.
- Uncertainty → mark assumptions and open questions.
