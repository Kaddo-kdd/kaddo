# Consolidate Tech Knowledge Baseline

## Current behavior

1. `.kaddo/modules.yml` does not exist — `loadMappedModules()` returns `[]`, and `kaddo verify`
   produces false-positive BLOCKED findings because `affected_modules` in WIs can't be resolved.

2. `knowledge/tech/codebase.md` was generated by `kaddo-bootstrap` and has open questions that
   have been answered since (e.g., scripts to run CLI+admin concurrently).

3. `knowledge/tech/current-state.md` was generated by `kaddo-bootstrap` and has open questions
   (deploy strategy, adapter config) and stale implicit decisions. Project state is listed as
   `pre-ai` but should be `ai-assisted`.

4. `knowledge/tech/` has no `stack.md` — agents working on Kaddo have no explicit stack
   reference for technology decisions.

5. `knowledge/tech/decisions/` and `knowledge/tech/discovery/` are empty `.gitkeep` dirs.

## Target behavior

1. `.kaddo/modules.yml` registers the 5 workspace packages as modules with id, name, path,
   type, mainTechnology, capabilities, and code paths. This fixes the `kaddo verify`
   false-positive blocker (friction #1 from WI-006).

2. `knowledge/tech/codebase.md` is refined: open questions closed, architecture-agent
   attribution updated.

3. `knowledge/tech/current-state.md` is refined: project_state set to `ai-assisted`, open
   questions resolved or removed, stale content updated.

4. `knowledge/tech/stack.md` created with the actual stack: Node.js, TypeScript, pnpm
   monorepo, Commander, Fastify, React, Vite, TailwindCSS, Vitest, Playwright, tsup, Zod,
   MCP SDK.

## Acceptance criteria

- [ ] AC1: `.kaddo/modules.yml` exists and registers at least the 5 workspace packages
- [ ] AC2: `loadMappedModules()` returns 5 modules when run against the project root
- [ ] AC3: `knowledge/tech/codebase.md` has no open questions
- [ ] AC4: `knowledge/tech/current-state.md` has project_state: ai-assisted and no open questions
- [ ] AC5: `knowledge/tech/stack.md` exists with the actual stack documentation
- [ ] AC6: `kaddo verify WI-008` no longer produces false-positive BLOCKED from unresolved modules

## Validation

- `pnpm --filter @kaddo/cli run test` passes
- `kaddo verify WI-008 --json` produces evidence without false-positive module blockers
- Manual review of all created/updated knowledge files

## Out of scope

- Creating per-module subdirectories under `knowledge/tech/modules/<id>/`
- ADR creation or security documentation
- Changes to CLI code beyond the modules.yml descriptor file

## Learning

1. La instalación de `.kaddo/modules.yml` fue la pieza más impactante de este WI — resuelve
   directamente la fricción significativa de WI-006 (false-positive BLOCKED en `kaddo verify`).
   Esto demuestra que los WIs del dogfooding se retroalimentan: el friction log de un WI
   anterior informó la priorización de este.

2. El refinamiento de knowledge existente (cerrar open questions en codebase.md y
   current-state.md) requirió descubrimiento real del codebase para responder correctamente.
   La complejidad "medium-complex" fue apropiada — no por la dificultad técnica, sino por la
   amplitud de descubrimiento necesario.

3. Actualizar `config.yml` de `pre-ai` a `ai-assisted` fue un cambio derivado no anticipado
   en el scope original. Esto es una scope deviation menor pero justificada — la consistencia
   entre config.yml y current-state.md es importante para `kaddo context`.
