# Work Item + Project Resource integration

Slice **D** de la épica [[WI-046]] (Controlled Deprecation). Depende de [[WI-047]], [[WI-048]], [[WI-049]].

## Intent

Conectar el plan con la ejecución: un plan produce WI candidates por wave; un WI materializado
referencia sus targets y, cuando aplica, sus Project Resources, y el Implementation Handoff conoce el
contexto de deprecación. El plan vive en el Core Project y abarca múltiples repos.

## Scope

- `deprecation_targets: [...]` en `WorkItemDetail` (trazabilidad WI → DEP → target), sin copiar la
  definición del target en el WI.
- **Materialización** de WI candidates desde el plan por wave.
- **Multirepo**: targets apuntan a módulos validados contra `.kaddo/modules.yml`; un plan abarca varios
  repos; no se duplica el plan en repos secundarios.
- **Resources**: targets database/external se vinculan a `resource: RES-…` y respetan sus boundaries
  (prod write/destructive → approval/runbook).
- **Implementation Handoff**: sección que incluye target / soft-state / usage-evidence / blast-radius /
  reversibility / environments / resources / rollback cuando el WI pertenece a un plan.

## Acceptance criteria

- [x] `deprecation_targets` con trazabilidad WI → DEP → target (AC-10).
- [x] Multirepo: targets validados contra modules.yml; un plan, varios repos (AC-03).
- [x] Targets database/external vinculados a Project Resources respetando boundaries (AC-04).
- [x] Handoff enriquecido con contexto de deprecación.
- [x] Tests (materialización por wave, validación de módulo, boundary de resource).

## Learning

La integración se hizo **por referencia, no por copia**: el WI lleva `deprecation_targets: [...]` (ids,
opcionalmente calificados por plan `DEP-001/DEP-TGT-001`) y el Core resuelve cada ref contra los planes
en tiempo de lectura. Así el target vive en un único lugar (el plan) y el WI solo apunta — misma
filosofía que `resources:[{id,role}]`. El parse acepta tres notaciones (string, `plan/target`, objeto)
para no forzar una sola forma a los agentes/humanos.

`parseWorkItemDeprecationTargets` se ubicó en `deprecation.ts` (el modelo es dueño de la forma) y
`work-items.ts` solo lo importa, evitando un ciclo (deprecation.ts no importa work-items). La
materialización (`proposeWorkItemCandidates`) agrupa por **(wave, módulo)** para que cada candidato sea
un WI → una rama → un PR, y en multirepo abane naturalmente a los repos dueños; los targets sin módulo
caen en un grupo final estable. Es derivación pura: proponer candidatos ≠ crear WIs (eso queda
human-gated vía create/import).

El Handoff reusó el patrón de la sección "Relevant Resources": una nueva "Relevant Deprecation Targets"
que, cuando el WI pertenece a un plan, informa lifecycle/environments/confianza de no-uso/blast-radius/
reversibilidad/`depends_on_removal` y el **boundary del Project Resource** asociado, con el recordatorio
explícito de que un cambio de producción exige Runbook + aprobación humana (sin ejecución autónoma). Un
target que no resuelve se **nota** en el texto, nunca se inventa — coherente con el principio de no
degradar lo desconocido.
