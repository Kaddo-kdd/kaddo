# WI-030 — Resources Core

Hijo de la épica [[WI-029]] (Project Resources). Entrega el **modelo canónico** y su reconocimiento en
Core; las superficies CLI/MCP, intelligence, graph/docs y Admin son hijos posteriores.

## Intent

### Problema

Kaddo no tiene un modelo explícito para los sistemas externos del proyecto (Supabase, AWS, Kafka,
APIs…). No puede responder qué recursos externos existen, por qué, en qué ambientes, cómo se accede y
con qué límites, ni relacionarlos con Work Items — distinto de `affected_modules` (código).

### Goal

Introducir **Project Resource** como conocimiento técnico first-class: un artifact bajo
`knowledge/tech/resources/` con identity/type/provider/purpose/environments/interfaces/boundaries, y
permitir que un WI declare `resources: [{id, role}]`. Core los reconoce y expone; no ejecuta nada.

## Product principle — Resource ≠ Access Interface ≠ Module

El recurso es la parte estable del sistema. CLI/MCP/SQL/API son **interfaces de acceso** (0..n por
recurso), no recursos. `affected_modules` = código; `resources` = sistemas externos. No convertir CLI/
MCP en recursos (`RES-supabase-cli` ✗) ni servicios externos en módulos solo para relacionarlos.

## Scope

1. **Discovery**: `discoverKnowledge` reconoce `type: project-resource` bajo `knowledge/tech/resources/`
   (layer `tech`, `isWorkItem: false`), sin tratarlos como WI ni como módulos.
2. **Resource read model** (`core/resources.ts`): `getResources(dir)` / `getResource(dir, id)` que
   devuelven identity (id, title), resource_type, provider, purpose, environments, access interfaces
   (tipo + tool/provider + purpose + operaciones + ambientes + constraints) y access boundaries,
   leyendo del frontmatter + secciones Markdown. Mínimo suficiente: `type/id/title/resource_type/
   provider` basta; el resto es opcional.
3. **Resource types** (validación laxa, extensible): `database|cloud|api|queue|storage|repository|
   platform|service|other`. Interface types: `cli|mcp|api|sql|sdk|iac|console|other`. Un solo contract
   para todos los providers.
4. **Security boundary**: el modelo admite referencias de auth (nombre de credencial/env var/secret
   reference/rol/boundary) pero **nunca** valores; `getResource` no resuelve secretos.
5. **WI relationships**: parsear `resources: [{id, role}]` del frontmatter del WI a `WorkItemDetail`
   (`resources: {id, role}[]`), roles `affected|implementation|validation|delivery` (un recurso puede
   repetirse con distinto rol). Mantener separado de `affectedModules`.
6. **Backward compatibility**: todo opcional; sin `knowledge/tech/resources/` ni `resources:` en el WI
   nada cambia (AC-06/14). `bootstrap` no genera recursos artificiales.

## Out of scope (de este hijo)

Comando/MCP de lectura (hijo surfaces); refinement/context/handoff (intelligence); graph/docs/evidence
(graph-docs); Admin. Y todo lo fuera de alcance de la épica (ejecución remota, credenciales, etc.).

## Acceptance criteria

- [x] AC-01 — Resource Artifact: Core reconoce `type: project-resource` bajo `knowledge/tech/resources/` (layer tech, no WI).
- [x] AC-02 — Resource Contract: el read model expone identity, resource_type, provider, purpose, environments, access interfaces y boundaries.
- [x] AC-03 — Secret Safety: admite referencias de auth; nunca requiere ni resuelve valores de credenciales.
- [x] AC-04 — Access Interfaces: un resource puede declarar múltiples interfaces (cli, mcp, api, sql, sdk, iac, console).
- [x] AC-05 — WI Relationships: `WorkItemDetail` expone `resources: [{id, role}]` con los 4 roles, separado de `affectedModules`.
- [x] AC-06 — Optional/Backward Compatible: proyectos sin resources funcionan igual; sin blockers ni migración.
- [x] AC-07 — Minimum Sufficient: un resource válido puede ser solo `type/id/title/resource_type/provider`.

## Validation

- Crear `knowledge/tech/resources/supabase-main.md` (database/supabase, interfaces CLI/MCP/PostgreSQL,
  auth ref `SUPABASE_ACCESS_TOKEN`) → `getResources`/`getResource` devuelven purpose/interfaces/
  boundaries y la **referencia** del token, nunca su valor; `discoverKnowledge` lo clasifica tech/no-WI.
- Un WI con `affected_modules: [api]` + `resources: [{id: RES-supabase-main, role: affected}]` →
  `WorkItemDetail` muestra módulo `api` y recurso `RES-supabase-main` (role affected) sin confundirlos.
- Un WI con el mismo recurso en dos roles → ambos preservados.
- Proyecto sin `knowledge/tech/resources/` → discovery y WorkItemDetail sin cambios ni errores.
- Suite de Core sin regresiones.

## Definition of Done

Core reconoce Project Resources; `core/resources.ts` expone el read model (sin secretos); el WI expone
`resources` separado de `affected_modules`; backward-compatible; tests de parsing + relaciones +
compatibilidad; Evidence recolectada; Verification pasa; Learning capturado.

## Implementation handoff guidance

Reutilizar el patrón de `discoverKnowledge` (tipo por frontmatter) y el de parsing de relaciones en
`work-items.ts` (como `parseRelatedKnowledge`). Decidir el reparto frontmatter vs. secciones Markdown:
recomendado frontmatter para identity/type/provider/environments + secciones `## Access Interfaces` /
`## Access Boundaries` en Markdown (legible, minimum sufficient). No exponer un `getResource` que
resuelva secretos. No agregar aún comando/MCP (hijo surfaces).

## Learning

- **Discovery ya era genérica.** No hizo falta tocar `knowledge-artifacts.ts`: `discoverKnowledge`
  resuelve el tipo por frontmatter y el layer por path, así que un `type: project-resource` bajo
  `knowledge/tech/resources/` queda layer `tech` y `isWorkItem: false` automáticamente. AC-01 salió
  gratis; `getResources` solo filtra por tipo.
- **Interfaces/boundaries en frontmatter estructurado, no en Markdown.** El spec mostraba secciones
  Markdown, pero como CLI/MCP/Graph/Admin van a **consumir** estas interfaces, modelarlas como
  `access_interfaces: [{type,tool,...}]` + `access_boundaries: {env:[...]}` en frontmatter es mucho más
  máquina-legible. El body Markdown queda para narrativa (`# Purpose`) y se expone verbatim
  (`markdownBody`) para display fiel. Decisión tomada en implementación; documentar el schema en el
  hijo graph/docs.
- **Secret safety defensivo.** `parseAuth` no solo lee `authentication.refs`: descarta cualquier
  entrada que parezca un valor (`NAME=value` o con caracteres no-identificador), así un error humano
  de poner `SUPABASE_DB_PASSWORD=...` en refs no filtra el secreto. Test lo cubre.
- **El contrato del admin-server tolera el campo nuevo.** `resources` en `WorkItemDetail` no rompió el
  schema zod (strip de claves desconocidas) — el contrato explícito + la UI se agregan en el hijo
  Admin (WI-034), manteniendo la separación por capas.
- **Release diferido.** Al ser el primer hijo sin superficie de usuario, no se bumpeó versión; el
  release de la épica se hará cuando aterricen superficies útiles (evita micro-releases).
