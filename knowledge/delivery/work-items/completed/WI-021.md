# WI-021 — Initiative external traceability, graph, docs y E2E

> Hijo de [WI-017](./WI-017.md) (epic). Cubre las fases 7-8: trazabilidad externa provider-neutral, grafo de trazabilidad, documentación EN/ES y dogfooding end-to-end. Cierra el epic.

## Intent

### Problema

Con Initiatives operables e inteligentes (WI-018/019/020), falta conectarlas con planificación externa (Jira/ADO/GitHub) de forma provider-neutral, representarlas en el Knowledge Graph, documentarlas y validar el flujo completo con Kaddo mismo.

### Goal

Dejar la trazabilidad externa preparada y utilizable (sin sincronización bidireccional ni import completo), extender el grafo, documentar EN/ES y ejecutar un escenario E2E de dogfooding.

## Scope

- **external_links** (AC-22): referencias provider-neutral `{ integration, external_id, external_type, url }` en el artifact de Initiative. No asumir `Initiative = Jira Epic`.
- **External status as signal** (AC-23): un estado externo (p.ej. Epic = Done) no cambia el lifecycle de la Initiative; se trata como señal; Kaddo conserva su lifecycle, análisis y human gate.
- **Imported WI association** (AC-24): cuando un WI importado se relaciona claramente con una Initiative, Kaddo sugiere la asociación (confirmación humana salvo regla determinística aprobada). Boundary adapter-neutral: `Provider → Adapter → normalized metadata → Core`, sin lógica de Jira en Initiative Core.
- **Graph** (AC-25): extender el Knowledge Graph con Initiative→capability, Initiative→WI, Initiative→external planning item, WI→Initiative, Candidate→Initiative, sin romper graph consumers existentes.
- **Docs** (AC-27): EN/ES — Initiative lifecycle, roadmap relationship, standalone WIs, CLI, MCP, Admin, external traceability.
- **E2E dogfooding**: ejecutar el flujo completo usando Kaddo sobre su propio repo; recolectar Implementation Evidence; capturar Learning del modelo de Initiative.

## Out of scope

- Sincronización bidireccional completa con Jira/ADO/GitHub.
- Propagación automática de estado externo.
- Capability completa de discover/import de ExternalPlanningItem.
- Lifecycle de Initiative específico por proveedor.

## Acceptance criteria

- [x] AC-22 — External Links: una Initiative mantiene referencias provider-neutral a Jira u otras integraciones.
- [x] AC-23 — External Status Isolation: cambios de status externos no modifican automáticamente el lifecycle.
- [x] AC-24 — Imported WI Association: Kaddo asocia o sugiere asociación de un imported WI con una Initiative.
- [x] AC-25 — Graph: relaciones Initiative → WI/capability/external representables sin romper graph consumers.
- [x] AC-27 — Documentation: docs EN/ES de Initiative lifecycle, roadmap relationship, standalone WIs, CLI, MCP, Admin y external traceability.

## Learning

### Decisiones de diseño

1. **external_status como señal, no como control (AC-23):** El campo se almacena y se muestra, pero ninguna lógica de Core lo consulta para cambiar el lifecycle. Esto hace la propiedad verificable con un test simple y mantiene el human gate: un Epic externo "Done" no completa la Initiative.

2. **Sugerencia determinista, asociación con confirmación (AC-24):** `suggestInitiativesForExternalItem` solo empareja por `integration` + `external_id` (case-insensitive) contra los `external_links`. No asocia nada automáticamente; devuelve candidatos para que el humano confirme. Boundary adapter-neutral: el Core no conoce Jira, solo referencias normalizadas.

3. **Nodos de Initiative keyed por `slug(ini.id)` (AC-25):** El grafo ya creaba un nodo `initiative:<slug>` desde el campo `initiative` del WI y un edge `belongs_to`. Al añadir el nodo real con el mismo id (`initiative:ini-001`) ANTES del loop de WIs, el nodo completo (con path/status) gana por `addNode` first-wins y los edges existentes resuelven al nodo real sin duplicar. Los tipos nuevos (`external-item`, `targets`, `references_external`) son aditivos a las uniones, así que los consumers no se rompen.

4. **Reutilización de `roadmap-candidate` para candidates de Initiative:** Los candidates de Initiative (WI-CANDIDATE-xxx) comparten concepto con los de roadmap, así que reutilizan ese tipo de nodo; el dedup por id evita duplicados cuando coexisten.
