## Intent

### Problema

Kaddo ya puede generar iniciativas candidatas dentro de `knowledge/delivery/roadmap.md`, asociar Work Item candidates a esas iniciativas y materializar candidatos mediante:

```bash
kaddo create --from roadmap
```

Los Work Items materializados desde roadmap conservan información de provenance como:

```text
source_roadmap_initiative
source_work_item_candidate
source_initiative_title
```

y los Work Items ya soportan metadata `initiative`.

Sin embargo, una iniciativa todavía no existe como entidad independiente y operable dentro de Kaddo.

Actualmente no existe una forma consistente de:

```text
crear una iniciativa directamente;
consultarla;
editarla;
asociarle Work Items;
ver cuánto trabajo ha sido materializado;
saber qué Work Items pertenecen a ella;
analizar qué falta para cumplirla;
generar nuevos WI candidates a medida que evoluciona el proyecto;
evaluar si realmente está completa;
operarla desde CLI, MCP o Admin;
trazarla con Jira u otros sistemas externos.
```

Esto limita el flujo:

```text
Knowledge
↓
Roadmap
↓
Work Items
```

porque falta una capa explícita que represente el outcome que conecta intención de producto con unidades ejecutables de delivery.

---

## Goal

Convertir `Initiative` en una entidad first-class de Kaddo que permita:

```text
Product Intent
      ↓
Initiative
      ↓
WI Candidates
      ↓
Work Items
      ↓
Implementation
      ↓
Verification
      ↓
Initiative Completion Review
```

manteniendo completamente válido el flujo actual:

```text
Idea
↓
Standalone Work Item
↓
Refinement
↓
Ready
↓
Implementation
↓
Verification
↓
Completed
```

Una iniciativa debe ser una capa opcional de trazabilidad, nunca un requisito para que un Work Item pueda existir o completar su lifecycle.

### Outcome framing

- **Actor:** Product owner / tech lead que organiza entregas, y agentes (roadmap/backlog/initiative) que proponen trabajo.
- **Current behavior:** El roadmap genera candidatos `RM-xxx` y `WI-CANDIDATE-xxx`; `kaddo create --from roadmap` materializa WIs con provenance; el read model de WI expone `initiative: string | null`. No existe la Initiative como entidad consultable, editable, analizable ni con lifecycle propio.

## Product Principles

### Initiative is optional

Debe seguir siendo válido crear:

```bash
kaddo create feature
```

sin seleccionar una iniciativa.

Un Work Item con `initiative:` vacío debe poder recorrer normalmente:

```text
draft → ready → implementation handoff → implementing → evidence → verification → completed
```

La ausencia de Initiative no debe generar readiness errors, bloquear Handoff/Verification/Completion ni invalidar Work Items existentes.

### Candidate ≠ committed artifact

Mantener la separación `Roadmap Candidate ≠ Initiative` y `WI Candidate ≠ Work Item`. Los agentes proponen; el humano decide qué materializar.

### Initiative completion ≠ all WIs completed

El hecho de que todos los Work Items conocidos estén completados no demuestra que el outcome de la Initiative se haya alcanzado. Kaddo debe evaluar scope, success criteria, conocimiento actual, cobertura de candidatos, WIs relacionados, evidencia de verificación, open questions y gaps conocidos antes de sugerir que una Initiative está completa. La transición final conserva Human-in-the-Loop.

## Target Model

### Initiative artifact

```text
knowledge/
└── delivery/
    ├── roadmap.md
    ├── initiatives/
    │   ├── INI-001-authentication-foundation.md
    │   └── ...
    └── work-items/
```

Ejemplo conceptual:

```yaml
---
type: initiative
id: INI-001
title: Authentication Foundation
status: planned
horizon: now
priority: high
knowledge_level: K2
domains:
  - Identity
related_capabilities:
  - User Authentication
source: roadmap
source_id: RM-001
created_at: 2026-10-02
external_links: []
---
```

Secciones del cuerpo: Goal, Expected Value, Scope, Out of Scope, Success Criteria, Dependencies, Work Item Candidates, Open Questions, Learning. La estructura exacta puede refinarse en el Handoff, pero debe conservar: identity, intent, scope, success criteria, dependencies, traceability, candidates, lifecycle, learning.

### Initiative Lifecycle

```text
candidate → planned → in-progress → completed
```

Estados alternativos: `deferred`, `cancelled`. Las iniciativas materializadas normalmente comienzan en `planned`. `candidate` puede quedar reservado para la representación de roadmap si evita duplicar conceptos. El Handoff define la representación más simple sin estados redundantes.

## Alcance detallado (secciones 1–24 del spec original)

1. **Roadmap → Initiative Materialization** — `roadmap-agent` sigue generando RM-xxx; materialización `RM-001 → human selection → INI-001` preservando `source: roadmap`, `source_id: RM-001`. `roadmap.md` sigue siendo la vista estratégica (Now/Next/Later/Not Now).
2. **Roadmap Remains Valid** — no romper `kaddo create --from roadmap`; compatibilidad con roadmaps históricos; sin migración manual inmediata.
3. **Initiative → Work Item Relationship** — WI referencia `initiative: INI-001`; relación opcional, many-WI→one-INI; resolución consultando artifacts (sin segunda lista manual).
4. **Work Item Candidates** — una Initiative contiene/relaciona candidates no materializados (id, title, type, suggested knowledge level, expected value, notes, source signals, dependencies, materialization status/reference); al materializar `WI-CANDIDATE-001 → WI-021` se conserva la relación.
5. **Planning vs Delivery Progress** — separar planning coverage (candidates materializados / totales) de delivery progress (estados de WIs asociados). Sin porcentaje arbitrario; sin asumir pesos iguales.
6. **Initiative Creation from CLI** — superficie CLI: `create, list, show, update, progress, analyze, candidates, materialize, complete` (nombres sujetos a convenciones actuales). Todo delega en Core.
7. **Initiative Creation from MCP / LLM** — capabilities equivalentes: `kaddo_list_initiatives`, `kaddo_get_initiative`, `kaddo_get_initiative_context`, `kaddo_get_initiative_progress`, `kaddo_create_initiative`, `kaddo_update_initiative`, `kaddo_analyze_initiative`, `kaddo_add_initiative_candidate`, `kaddo_materialize_initiative_candidate`, `kaddo_complete_initiative`. Reutilizan reglas de Core.
8. **Human Confirmation for MCP Mutations** — los agentes analizan/proponen/preview/explican; no materializan cambios estratégicos silenciosamente; mutaciones relevantes siguen los patrones de confirmación existentes (confirm=true).
9. **Initiative Context** — contexto dinámico ensamblado por Knowledge Levels (business/product knowledge, related capabilities, arquitectura relevante, System Graph cuando exista, candidates, WIs asociados/completados, evidencia, verificación, learning, open questions, risks). No cargar todo el proyecto.
10. **Initiative Agent** — `initiative-agent`: entender, evaluar cobertura, descomponer en candidates, detectar trabajo faltante y candidatos duplicados/solapados, considerar estado actual, evaluar completion readiness, sugerir candidates. No escribe código de producción, no materializa WIs sin decisión humana, no marca completed autónomamente.
11. **Incremental Gap Analysis** — una Initiative puede analizarse múltiples veces; el análisis considera el estado actual del proyecto, no solo la definición original.
12. **Candidate Generation from Current State** — ante "¿qué falta para completar INI-001?", producir coverage analysis (success criteria cubiertos/no, delivery existente, uncovered scope, candidates sugeridos) justificado por conocimiento/gaps. No inventar trabajo sin source signals.
13. **Materialization of New Candidates** — `Gap → Candidate → Human selection → Work Item` desde CLI/MCP/Admin, conservando source initiative, source candidate, domain, related capabilities, source signals.
14. **Backlog Agent Integration** — `backlog-agent` distingue: idea nueva → ¿pertenece a Initiative existente? → sí (sugerir candidate/asociación) / no (standalone WI o new Initiative candidate). No obliga a clasificar todo bajo Initiative.
15. **Completion Readiness** — evaluación explícita: success criteria, candidate coverage, WIs asociados y su lifecycle, verificación, blocking open questions, risks/gaps, conocimiento actual.
16. **Human Completion Gate** — cuando parece completa → completion candidate → human review → completed. Nunca cambia a `completed` automáticamente.
17. **Initiative Learning** — al completar, registrar learning (qué se entregó, qué quedó fuera, si se alcanzó el valor esperado, desviaciones, conocimiento nuevo, iniciativas/trabajo descubierto). Diferenciar `delivery completed` de `business outcome validated` cuando falte evidencia.
18. **Admin Initiative Management** — sección Initiatives: list, lifecycle/status, horizon/priority, create, edit, candidates, WIs asociados, planning coverage, delivery progress, analysis, materialize candidates, completion readiness. Consume Core.
19. **Standalone Work Items in Admin** — WIs sin Initiative se muestran normalmente (etiquetables como "Standalone"/"No Initiative"), nunca como error.
20. **External Initiative Traceability** — `external_links` provider-neutral (integration, external_id, external_type, url). No asumir `Kaddo Initiative = Jira Epic`.
21. **External Status as Signal** — estado externo no cambia automáticamente el lifecycle; se trata como señal. Kaddo conserva su lifecycle, análisis y human gate.
22. **Imported Work Item Association** — cuando un WI importado se relacione claramente con una Initiative, Kaddo sugiere la asociación (confirmación humana salvo regla determinística aprobada).
23. **Integration Adapter Boundary** — sin lógica específica de Jira en Initiative Core; `Provider → Adapter → normalized external metadata → Kaddo Core`.
24. **Graph and Traceability** — extender el Knowledge Graph (Initiative→capability, Initiative→WI, Initiative→external planning item, WI→Initiative, Candidate→Initiative) sin romper graph consumers existentes.

## Out of scope

```text
hacer Initiative obligatoria;
convertir Kaddo en un project management system;
sprints / story points / velocity / capacity / burndown;
team assignment / resource management;
priorización automática por esfuerzo;
completion automática de Initiative;
creación automática de Work Items sin confirmación humana;
sincronización bidireccional completa con Jira/Azure DevOps/GitHub;
propagación automática de estado externo;
lifecycle de Initiative específico por proveedor;
capability completa de discover/import de ExternalPlanningItem;
analytics de business outcome no disponibles aún.
```

La importación completa `External Epic/Feature/Milestone → discover → preview → import → Kaddo Initiative` queda fuera de alcance. Este WI solo debe dejar preparada y utilizable la trazabilidad externa.
