# WI-022 — Initiative Admin: sección de gestión visual

> Hijo de [WI-017](./WI-017.md) (epic). Cubre la fase 6 (AC-15), separada de [WI-020](../completed/WI-020.md) el 2026-10-03 para darle verificación en navegador. Consume el Initiative Core (WI-018) y las superficies/analysis (WI-019/020) vía el Admin→Core adapter.

## Intent

### Problema

El Initiative Core, sus superficies CLI/MCP y la inteligencia (gap/completion analysis) existen (WI-018/019/020), pero el Admin no tiene forma de gestionar Initiatives visualmente. Falta la sección Initiatives en el Admin.

### Goal

Agregar una sección Initiatives al Admin que consuma el Core (sin lógica duplicada): listar, ver detalle, candidates, WIs asociados, planning/delivery progress, análisis y completion readiness — y crear/editar Initiatives.

## Scope

- **Contracts** (`packages/admin-server/src/contracts/schemas.ts`): schemas Zod para Initiative list item, detail (con progress + candidates + WIs asociados), analysis y completion readiness.
- **Core-adapter** (`core-adapter.ts`): `getInitiativesListAdmin`, `getInitiativeDetailAdmin` (incluye progress + analysis + completion), y las mutaciones `createInitiativeAdmin` / `updateInitiativeAdmin` reutilizando `@kaddo/cli/core`.
- **Server** (`server.ts`): rutas GET (`/api/v1/admin/initiatives`, `/api/v1/admin/initiatives/:id`) y las POST/PUT para create/update, siguiendo el patrón `coreRoute`.
- **API client** (`packages/admin/src/lib/api.ts`): métodos + tipos.
- **Rutas React**: `routes/Initiatives.tsx` (list) y `routes/InitiativeDetail.tsx` (detail con progress, candidates, WIs asociados, analysis y completion readiness). Wiring en `App.tsx` (TanStack Router) y entrada en `Sidebar.tsx`.
- **Standalone WIs** (AC-19 del epic / nota): los WIs sin Initiative se siguen mostrando normalmente en su propia vista; no se tratan como error.

## Out of scope

- Nueva lógica de dominio (vive en Core; el Admin solo presenta/consume).
- external_links / graph / docs / E2E (WI-021).

## Acceptance criteria

- [x] AC-15 — Admin: el Admin permite listar, consultar, crear/editar y seguir Initiatives (lifecycle/status, horizon/priority, candidates, WIs asociados, planning coverage, delivery progress, análisis y completion readiness), consumiendo Core.

## Evidence

- **Contracts**: `InitiativeCreateSchema` / `InitiativeUpdateSchema` en `packages/admin-server/src/contracts/schemas.ts` (validación de input POST/PUT).
- **Core-adapter** (`core-adapter.ts`): `getInitiativesListAdmin`, `getInitiativeDetailAdmin` (progress + candidates + WIs asociados + analysis + completion), `createInitiativeAdmin`, `updateInitiativeAdmin` — reutilizan `@kaddo/cli/core`; errores mapeados a `CoreError` (INITIATIVE_NOT_FOUND→404, INVALID_INITIATIVE_ID/INITIATIVE_WRITE→400).
- **Server** (`server.ts`): GET `/api/v1/admin/initiatives`, GET/PUT `/api/v1/admin/initiatives/:id`, POST `/api/v1/admin/initiatives`; `statusForCode` extendido.
- **API client** (`api.ts`): tipos `InitiativeListItem`/`InitiativeDetail` + métodos `getInitiatives`, `getInitiative`, `createInitiative`, `updateInitiative`.
- **React**: `routes/Initiatives.tsx` (list + create inline) y `routes/InitiativeDetail.tsx` (progress, completion readiness, analysis con findings, candidates, WIs asociados, external links, transiciones de estado); wiring en `App.tsx` + entrada en `Sidebar.tsx`.
- **Verificación en navegador** (requisito del WI): `kaddo admin` sobre un proyecto seed con 2 Initiatives (una con candidate materializado, WI asociado, external link, success criteria). La lista renderiza id/título/status/planning/delivery; el detalle renderiza Progress (1/2 · 0/1), Completion readiness ("Not ready" con 3 razones), Analysis (3 findings blocking con items), Move-to, candidates, WIs y external links. API JSON verificada. `tsc -b` del admin sin errores de tipos; `vite build` verde.

## Learning

### Decisiones de diseño

1. **Admin como presentación pura sobre Core:** El core-adapter no duplica lógica — compone `computeInitiativeProgress`, `analyzeInitiative`, `evaluateInitiativeCompletion`, `associatedWorkItems` del Core en un `InitiativeDetailAdmin`. La UI solo presenta. `updateInitiativeAdmin` enruta `status` por `transitionInitiative` (valida transiciones) y el resto por `updateInitiative`, replicando el patrón de WI-019.

2. **Detalle = un solo GET componible:** En vez de múltiples endpoints (progress, analysis, completion por separado), `getInitiativeDetailAdmin` devuelve todo en un payload, simplificando la UI (una query) a cambio de un objeto mayor — razonable para una herramienta local.

3. **Transiciones en el detalle según el lifecycle:** Los botones "Move to" se derivan de `NEXT_STATUS` (las transiciones válidas), evitando ofrecer saltos inválidos; el backend igual los valida.

### Observaciones (operacional, no código)

- `kaddo admin` sirve copias **bundled** en `packages/cli/dist/admin-dist` y `packages/cli/dist/admin-server/index.js`, que un build por-paquete no regenera; quedaron stale en la verificación hasta refrescarlas desde `packages/admin/dist` y `packages/admin-server/dist`. En release esto lo cubre `pnpm -r build`. No es un defecto del código de este WI; se documenta para quien verifique localmente tras builds parciales.
- Son artifacts gitignored (no se commitean).

- WIs standalone (sin Initiative) siguen mostrándose en su vista sin errores.
- Build del Admin verde (`tsc -b && vite build`) + tests existentes del Admin sin regresión.
