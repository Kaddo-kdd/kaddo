# WI-036 — Resource management Core + multirepo contract

Hijo de [[WI-035]]. Entrega el **contrato Core de mutación** y el modelo multirepo; CLI/MCP/Admin son
hijos posteriores que lo consumen. Markdown sigue siendo la única fuente de verdad.

## Intent

### Problema

El alta/mantenimiento de un Project Resource depende de editar su Markdown a mano. No hay un contrato
Core determinístico para crear/actualizar/eliminar recursos con validación, serialización segura y
chequeos de referencias, ni un modelo de scope (system/module) para multirepo.

### Goal

Agregar a Core `createResource`/`updateResource`/`deleteResource` + un modelo `scope`/`modules` y las
validaciones compartidas, de modo que todas las interfaces converjan en una sola fuente de reglas y el
artifact canónico viva en `knowledge/tech/resources/`.

## Scope

1. **Mutation contract** (`core/resource-write.ts`): `createResource(dir, input)`,
   `updateResource(dir, id, input)`, `deleteResource(dir, id, {confirm})` — determinísticos, sin red.
2. **ID gen/validación**: `nextResourceId`/normalización `RES-<slug>`; detección de duplicados (id y
   título).
3. **Resource Contract validation**: resource_type e interface types contra los sets conocidos (laxo/
   extensible), environments, secret-safety (rechazar valores en `authentication.refs`, como ya hace
   `parseAuth`), y serialización Markdown **no-lossy** (preservar secciones/keys desconocidas).
4. **Scope/module model**: `scope: {type: system}` o `scope: {type: module, module: <id>}` + `modules:
   [...]` (uso por módulos). Ownership/scope ≠ dependencia.
5. **Module validation**: validar `module`/`modules` contra `.kaddo/modules.yml` (`loadMappedModules`)
   cuando exista → known / unknown / unavailable-mapped-repo; findings no bloqueantes salvo referencia
   claramente inexistente. Sin acceso remoto.
6. **Delete safety**: antes de borrar, `getResourceReferences(dir, id)` = WIs que lo referencian
   (`parseWorkItemResources`) + módulos relacionados. `deleteResource` sin `confirm` → preview de
   referencias; con `confirm=true` → borra solo el artifact del recurso (NO toca referencias de otros).
7. **Read model extendido**: `getResource` expone `scope` y `modules` (aditivo).

## Out of scope (de este hijo)

CLI interactivo (WI-037); MCP/LLM (WI-038); Admin (WI-039); aristas module→resource en el Graph y docs
(WI-040). Ejecución remota, credenciales.

## Acceptance criteria

- [x] AC-01 — Core create: `createResource` persiste un recurso Markdown canónico válido bajo `knowledge/tech/resources/`.
- [x] AC-02 — Core update: `updateResource` modifica sin pérdida (no-lossy) y revalida.
- [x] AC-03 — Core delete + safety: `deleteResource` sin confirm devuelve referencias; con confirm borra solo el artifact.
- [x] AC-04 — Progressive/minimum sufficient: crear acepta `type/id/title/resource_type/provider`; el resto opcional.
- [x] AC-05 — Secret safety: ninguna mutación acepta/persiste valores de credenciales (solo referencias).
- [x] AC-06 — Scope model: un recurso puede ser `scope: system` o `scope: module/<id>` y declarar `modules`.
- [x] AC-07 — Module validation: `module`/`modules` se validan contra `.kaddo/modules.yml` cuando exista (known/unknown).
- [x] AC-08 — Duplicate detection: crear un id/título duplicado es rechazado con un error claro.
- [x] AC-09 — Backward compatible: recursos/WIs existentes (sin scope) siguen leyéndose igual.

## Validation

- `createResource` (Supabase Main/database/supabase/system) → archivo canónico; `getResource` lo
  devuelve normalizado con `scope: system`.
- `createResource` con `scope: {type: module, module: orders-api}` en proyecto con ese módulo → OK;
  con `module: unknown-api` → validation finding, no se registra relación falsa.
- `updateResource` agrega `access_interfaces` sin perder el resto del frontmatter/body.
- `deleteResource(id)` con un WI que referencia el id → preview con la referencia; con `confirm` borra
  solo el recurso (el WI queda intacto).
- Secret: `refs: [TOKEN, "PWD=secret"]` → persiste solo `TOKEN`.
- Proyecto sin modules.yml / sin scope → sin errores.

## Definition of Done

Core expone create/update/delete con validación, scope/module y delete-safety; Markdown canónico
no-lossy; sin secretos; backward-compatible; tests de Core cubriendo mutaciones, scope/module
validation, duplicados, delete safety y secret safety; Evidence; Verification; Learning.

## Implementation handoff guidance

Espejar `work-item-write.ts` (`atomicWrite`, `serialize`, merge no-lossy) y reutilizar `resources.ts`
(read model, `parseAuth`, `parseWorkItemResources`) y `loadMappedModules`. No escribir Markdown por
fuera de este contrato. No agregar aún CLI/MCP/Admin.

## Learning

- **El contrato de mutación salió de espejar `work-item-write.ts`.** `createResource`/`updateResource`/
  `deleteResource` en `core/resource-write.ts` reutilizan `atomicWrite` + `matter.stringify` + merge
  no-lossy (preserva keys/body desconocidos) exactamente como los writes de WI. ID = `RES-<slug>` con
  desduplicación por sufijo numérico.
- **Secret-safety en el WRITE, no solo en el read.** `buildFrontmatter` sanea `authentication.refs`
  (descarta `NAME=value`/no-identificadores) antes de persistir, así un valor nunca llega al Markdown.
  Doble barrera con el `parseAuth` del read model.
- **Scope ≠ dependencia.** El modelo agrega `scope: {type, module}` (ownership) y `modules: [...]`
  (uso), separados. Validación contra `.kaddo/modules.yml` vía `loadMappedModules`: findings
  **advisory** (warning) salvo `scope.module` ausente (error) — no bloquea por un módulo desconocido,
  pero lo señala.
- **Delete safety sin efectos ocultos.** `deleteResource` sin `confirm` devuelve las referencias (WIs
  que lo enlazan vía `parseWorkItemResources`); con `confirm` borra **solo** el artifact del recurso y
  deja intactas las referencias de otros artifacts. El test lo afirma.
- **Read model extendido aditivo.** Agregar `scope`/`modules` a `ResourceSummary`/`ResourceDetail` no
  rompió nada (1491 verdes); los hijos CLI/MCP/Admin/graph ya pueden consumirlo.
