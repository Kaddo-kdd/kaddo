# Estandarizar contribuciones con un Work Item por rama y Pull Request

## Intent

### Problema

Kaddo se construye con su propio Knowledge-Driven Development y Build Contract, pero el proceso de
contribución no conecta explícitamente ese conocimiento con el flujo normal de GitHub. Un contributor
puede crear una rama y abrir un PR, pero no hay convención que garantice que cada PR represente un
cambio coherente, que el contributor entienda el contexto antes de implementar, que exista una
definición clara del cambio y sus Acceptance Criteria visibles para el reviewer, que la PR conserve
trazabilidad con el Work Item, y que el scope no mezcle varios outcomes independientes.

### Goal

Extender el modelo KDD al proceso de contribución mediante una regla simple:
**One Work Item → One Branch → One Pull Request**. El Work Item actúa como contrato de intención,
alcance y aceptación. El reviewer entiende primero why / what / scope / out of scope / acceptance
criteria / validation / knowledge impact, antes de revisar el diff.

## Contribution principle — One Work Item → One Branch → One Pull Request

Una contribución representa un único outcome coherente. No significa "PR pequeño" sino "un Work Item
coherente" (un WI K3/K4 puede justificar una PR grande). Lo que se evita es mezclar feature A +
refactor no relacionado + bug B + cambio de docs C cuando son outcomes independientes.

## Actor y outcome

- **Actor**: un contributor (interno o externo) que quiere proponer un cambio a Kaddo; y el
  maintainer/reviewer que evalúa la PR.
- **Outcome observable**: `CONTRIBUTING.md` describe el flujo Work Item-driven y existe
  `.github/PULL_REQUEST_TEMPLATE.md`, de modo que una PR nueva trae la intención, scope, ACs,
  validación y knowledge impact del WI que la origina — y el reviewer revisa contra ese WI, no solo
  contra el diff. Sin cambios en Kaddo Core ni automatización Git.

## Current behavior

`CONTRIBUTING.md` (135 líneas) ya documenta Setup, Build, Principles, "What you can contribute",
"What requires a discussion first", el **Build Contract** (los 7 pasos del lifecycle) y Releasing.
Pero no conecta ese lifecycle con el flujo de GitHub del contributor, y **no existe un PR template**
(`.github/` solo contiene `workflows/`), así que una PR no trae intención/scope/ACs de forma
estructurada y el review recae sobre el diff.

## Target behavior

`CONTRIBUTING.md` gana una sección "Contribution Workflow" (One WI → One Branch → One PR) que se
apoya en el Build Contract existente, y `.github/PULL_REQUEST_TEMPLATE.md` estructura cada PR con
WI reference/definition, Initiative (si aplica), ACs, Validation, Knowledge impact y checklist.

## Entry points (grounding técnico)

- `CONTRIBUTING.md` — agregar "## Contribution Principle" y "## Contribution Workflow"; **referenciar
  (no duplicar)** "## Build Contract: the Kaddo-native workflow" y "## What requires a discussion
  first" ya presentes. Añadir la convención de ramas y la regla de scope growth.
- `.github/PULL_REQUEST_TEMPLATE.md` (NUEVO) — GitHub lo usa automáticamente al abrir una PR; incluir
  WI reference/definition (`<details>` colapsable), Initiative, ACs, Validation, Knowledge impact y
  checklist. Breve.
- `examples/README.md` (o un ejemplo breve ahí) — el ejemplo de flujo (WI existente vs. definición
  embebida), reutilizando el set de ejemplos ya presente (`basic`, `new-project`, …).

## Surface review

- **Documentación / proceso** (afectado): `CONTRIBUTING.md`, ejemplos.
- **GitHub repo config** (afectado): nuevo `.github/PULL_REQUEST_TEMPLATE.md`.
- **Kaddo Core / CLI / MCP / Admin** (no afectado, AC-15): sin comandos nuevos ni automatización.
- **CI / workflows** (no afectado): el WI no valida PRs por Actions (fuera de alcance).
- **Knowledge artifacts** (no forzado): solo si el cambio lo justifica.

## Scope

1. **Knowledge first**: la guía recomienda usar el conocimiento del propio proyecto (Business,
   Product, Tech, Architecture, Capabilities, Initiatives, Roadmap, Completed WIs, Learning) vía CLI,
   MCP, agentes o el LLM del contributor, antes de definir/implementar. No exigir leer todo el repo.
2. **Define the WI before coding**: antes de un cambio relevante debe existir una definición
   proporcional (Intent/Problem, target outcome, scope, out of scope cuando aplique, ACs,
   validation). Cambios triviales → definición ligera; complejos → su nivel de conocimiento.
3. **Planned contributions**: si el trabajo ya está definido en Kaddo (Initiative → WI canónico), el
   contributor **referencia** el WI existente; la PR no duplica identidad.
4. **New/external contributions**: un contributor puede proponer trabajo sin WI canónico; incluye la
   definición del WI en la PR. No se exige crear/commitear un `WI-xxx` canónico (evita conflictos de
   numeración entre forks/ramas); el maintainer decide después si materializarlo en la trazabilidad.
5. **Branch convention**: una rama dedicada por WI (p. ej. `feat/…`, `fix/…`, `docs/…`). Git sigue
   siendo responsabilidad del contributor; Kaddo Core NO gestiona ramas.
6. **Scope growth**: trabajo adicional descubierto se evalúa contra el WI/ACs; si no pertenece →
   nuevo WI + nueva rama + nueva PR. No ampliar silenciosamente la contribución.
7. **PR template**: agregar `.github/PULL_REQUEST_TEMPLATE.md` que permita registrar WI
   reference/definition, Initiative cuando aplique, Acceptance Criteria, Validation, Knowledge impact
   y un checklist. Breve y útil.
8. **Embedded WI definition**: cuando no haya WI canónico, incluir la definición en la PR, preferible
   en una sección `<details>` colapsable para no dificultar la lectura.
9. **Review against intent**: la doc indica que el review no evalúa solo el código, sino si la
   implementación satisface el WI (intención, scope, ACs, validation/evidence) sin scope no declarado.
10. **Knowledge impact**: toda PR considera si cambia conocimiento (Business/Product/Tech/Delivery) y
    actualiza los artifacts relevantes; sin documentación forzada cuando no aplica.
11. **Existing discussion rules**: mantener las reglas actuales de `CONTRIBUTING.md` ("What requires a
    discussion first"). El WI no sustituye la discusión necesaria.
12. **Update CONTRIBUTING**: incorporar una sección "Contribution Workflow" (start from main →
    entender knowledge → definir/seleccionar un WI → discutir cuando aplique → una rama por WI →
    refine/handoff si aplica → implementar → validar/verificar → una PR por WI → incluir
    definición/referencia del WI y evidencia), conservando la explicación del Build Contract.
13. **Contribution example**: agregar al menos un ejemplo breve del flujo, mostrando tanto el caso con
    WI existente como el caso con definición embebida en la PR.

## Out of scope

Crear `kaddo contribute`; crear ramas/PRs automáticamente; materializar WIs desde PRs; validar el
contenido de la PR por GitHub Actions; crear IDs WI exclusivos para forks; sincronizar estado de PR
con el lifecycle del WI; modificar Kaddo Core; crear una metodología distinta a KDD; hacer obligatorio
un Initiative para contribuir. (Evaluables después de observar el flujo con contributors reales.)

## Validation

- **Planned contribution**: dado `WI-045` existente → el contributor lo lee, crea rama dedicada,
  implementa, abre PR, referencia WI-045, incluye validación/evidencia.
- **New contribution**: propuesta de mejora de scanner → lee knowledge, define un WI proporcional,
  crea rama, implementa, abre PR con la definición embebida. No se exige `WI-xxx` canónico antes del
  review.
- **Scope growth**: durante un WI de scanner se descubre una mejora no relacionada del Admin → no se
  agrega en silencio; el contributor crea/propone un WI y PR separados.
- **PR template**: crear una PR de prueba y confirmar que el template expone Work Item,
  Initiative/reference, Validation, Knowledge impact y Checklist, sin ser un formulario excesivo.

## Definition of Done

- `CONTRIBUTING.md` describe el flujo Work Item-driven; una contribución = un WI/outcome coherente;
  se documenta una rama y PR por WI; contributors pueden trabajar con WIs existentes o nuevas
  propuestas; los externos no necesitan reclamar un `WI-xxx` canónico antes del review.
- Existe un Pull Request template con definición/referencia del WI, validación y knowledge impact.
- Las reglas existentes de discusión previa se conservan; scope creep tiene regla explícita; existe
  al menos un ejemplo del flujo; no se agregan comandos ni automatizaciones Core innecesarias.
- El flujo se prueba al menos con una contribución real o simulada; Learning registra fricciones.

## Implementation handoff guidance

Enfocar en `CONTRIBUTING.md` + `.github/PULL_REQUEST_TEMPLATE.md` + ejemplos/documentación. No
convertir el flujo en una capability técnica todavía (Convention → contributors reales → observar
fricción → automatización futura si se justifica). El PR template no debe duplicar toda la
información del WI cuando exista uno canónico: para WIs existentes, referenciar + solo contexto/
evidencia útil; para contribuciones nuevas, embeber una definición proporcional.

## Learning

- **Integrar > duplicar.** `CONTRIBUTING.md` ya tenía el Build Contract (los 7 pasos del lifecycle) y
  "What requires a discussion first". El "Contribution workflow" nuevo los **referencia** en vez de
  repetirlos: define el flujo de GitHub del contributor (knowledge → WI → rama → PR → review contra
  intención) y delega el detalle del lifecycle al Build Contract. Así no hay dos fuentes que mantener.
- **El PR template vive donde GitHub lo autodetecta.** `.github/PULL_REQUEST_TEMPLATE.md` se aplica
  solo por su ruta; no hace falta ninguna config ni Action (coherente con AC-15: cero automatización).
- **La doble vía planned/new resuelve el conflicto de IDs.** Para trabajo canónico se **referencia**
  `WI-xxx`; para contribuciones externas se **embebe** la definición en la PR (`<details>`), sin
  crear un `WI-xxx` en el fork — evita choques de numeración entre forks/ramas y deja al maintainer
  decidir la materialización.
- **El ejemplo quedó inline en CONTRIBUTING** (decisión confirmada) con el caso de scope growth
  (mejora de Admin no relacionada → WI/rama/PR aparte), que es justo la fricción que este WI previene.
- **Nota de proceso.** El `## Validation` del WI pide "crear una PR de prueba"; no se creó una PR
  descartable real (sería ruido en el repo). La validación fue estructural (ruta estándar + secciones
  del template); la primera PR real ejercitará el template de forma natural.
- **Corregí de paso** la nota obsoleta de "Releasing" (`.version()` en src/index.ts) ya que tocaba el
  mismo archivo y era un dato incorrecto para contributors.
