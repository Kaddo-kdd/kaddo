# WI-014 — Integrar Kaddo con Kaddo Telemetry Service usando su Knowledge Capsule

## Intent

### Actor

Usuario de Kaddo que acepta compartir telemetría anónima sobre el uso del toolkit.

### Problema

Kaddo ya cuenta con un Telemetry Service desplegado bajo `https://telemetry.kaddo.org` pero el toolkit todavía no consume este servicio de forma nativa. El servicio expone su conocimiento de integración mediante una Knowledge Capsule que debe importarse y utilizarse como fuente de contexto.

## Acceptance criteria

- [x] AC-01: Knowledge Capsule de kaddo-telemetry registrada como External Knowledge
- [x] AC-02: Implementation Handoff utiliza la cápsula como contexto
- [x] AC-03: Telemetry puede habilitarse y deshabilitarse explícitamente
- [x] AC-04: Identidad anónima de instalación sin identidad personal
- [x] AC-05: Requests cumplen el contrato publicado por la Knowledge Capsule
- [x] AC-06: Kaddo puede enviar eventos válidos a telemetry.kaddo.org
- [x] AC-07: Eventos contienen únicamente metadata allowlisted, no contenido sensible
- [x] AC-08: Superficies de Kaddo reutilizan una única capability de telemetry en Core
- [x] AC-09: Errores de telemetría nunca fallan la operación principal
- [x] AC-10: Buffer local acotado para eventos no entregados
- [x] AC-11: Conjunto inicial de eventos que cubre operaciones relevantes
- [x] AC-12: Signing y anti-replay según contrato de kaddo-telemetry
- [x] AC-13: Kaddo funciona correctamente sin conectividad
- [x] AC-14: Documentación EN/ES sobre telemetría
- [x] AC-15: Learning documenta la experiencia de consumir una Knowledge Capsule

## Out of scope

- Analytics dashboard, lifecycle metrics UI
- Organization telemetry, cross-project analytics
- User tracking, source code/prompt collection
- Changes to the Telemetry Service

## Evidence

### AC-01: Knowledge Capsule registrada
- `knowledge/external/kaddo-telemetry.capsule.md` importada con `kaddo capsule add`
- `.kaddo/external.yml` contiene la referencia

### AC-03: Habilitar/Deshabilitar
- `kaddo telemetry enable` → escribe `telemetry.enabled: true` en `.kaddo/config.yml`
- `kaddo telemetry disable` → escribe `telemetry.enabled: false`
- `kaddo telemetry status` → muestra estado actual

### AC-04: Identidad anónima
- Ed25519 key pair generado con `crypto.generateKeyPairSync('ed25519')`
- UUID v4 como installationId, sin datos personales
- Almacenado en `.kaddo/telemetry/identity.json` (gitignored)
- Tests verifican formato UUID y persistencia

### AC-05 + AC-12: Contrato y signing
- POST a `/v1/installations` para registro, `/v1/events` para eventos
- Headers: `X-Kaddo-Installation-Id`, `X-Kaddo-Timestamp`, `X-Kaddo-Nonce`, `X-Kaddo-Signature`, `X-Kaddo-Key-Algorithm`
- Canonical string: `POST\n<path>\n<installationId>\n<timestamp>\n<nonce>\n<sha256Hex>`
- Test verifica firma Ed25519 con `crypto.verify()`

### AC-07: Propiedades allowlisted
- `AllowlistedProperties` type union en `telemetry-events.ts`
- Solo: command, durationMs, interface, workItemId, lifecycle event booleans
- No source code, no prompts, no PII

### AC-09: Best-effort
- Todas las funciones públicas envueltas en try/catch
- Fallos silenciosos, eventos se bufferizan para retry

### AC-10: Buffer acotado
- Máximo 100 eventos en `.kaddo/telemetry/buffer.json`
- Test verifica que 120 eventos se truncan a 100

### AC-11: Eventos instrumentados
- `command_executed` para cada comando (con duración)
- Lifecycle: `work_item_created`, `work_item_ready`, `work_item_completed`, `verification_completed`, `knowledge_generated`
- Capsule: `capsule_exported`, `capsule_imported`

### AC-13: Funcionamiento offline
- `isEnabled()` retorna false si no hay config
- Fallos de red se bufferizan silenciosamente
- 10 tests pasan sin conectividad

### AC-14: Documentación
- `apps/docs/src/content/docs/telemetry.md` (EN)
- `apps/docs/src/content/docs/es/telemetry.md` (ES)
- Sidebar entry en `astro.config.mjs`

## Learning

### Decisiones de diseño

1. **Ed25519 con crypto nativo:** Node.js 15+ soporta Ed25519 nativamente. No se necesitó dependencia externa. La exportación de clave pública en SPKI DER (44 bytes, base64url) fue directa con `crypto.generateKeyPairSync`.

2. **postAction hook para instrumentación:** Commander.js ofrece `hook('postAction')` que se ejecuta después de cada comando. Esto permitió instrumentar todos los comandos existentes sin modificar sus archivos individuales — un solo punto de enganche en `index.ts`.

3. **Lookup tables para mapeo de eventos:** En vez de lógica condicional compleja, dos objetos planos (`LIFECYCLE_EVENTS`, `CAPSULE_EVENTS`) mapean nombre de comando a tipo de evento. Simple, extensible, legible.

4. **Buffer basado en archivo:** `.kaddo/telemetry/buffer.json` con límite de 100 eventos. Sin dependencia de base de datos. El archivo se lee/escribe atómicamente, lo cual es suficiente para uso CLI (no concurrente).

5. **Config con `.passthrough()`:** Zod schema para telemetry usa `.passthrough()` para permitir extensibilidad futura sin romper schemas existentes.

### Experiencia consumiendo una Knowledge Capsule (AC-15)

La Knowledge Capsule de kaddo-telemetry funcionó como contrato de integración completo:

- **Contrato de API explícito:** Los endpoints, payloads, headers y formato de firma estaban completamente documentados. No hubo ambigüedad sobre cómo construir el canonical string ni qué formato usar para la clave pública.

- **Riesgos y dependencias documentados:** La cápsula incluía secciones de riesgos (rate limiting, key rotation) y dependencias (DNS, TLS) que informaron decisiones de diseño como el buffer local.

- **Brechas descubiertas en desarrollo:**
  - El config schema de Kaddo no incluía `ai-assisted` como estado válido de proyecto, lo cual bloqueó `kaddo capsule add` en el propio repositorio de Kaddo. Se corrigió agregando el estado al enum.
  - La cápsula no documenta explícitamente el comportamiento del servicio cuando recibe un batch con eventos que tienen timestamps muy antiguos (eventos buffered).

- **Valor como contexto de implementation:** La cápsula proporcionó suficiente contexto para implementar la integración completa sin necesidad de consultar documentación externa ni el código fuente del servicio.

### Observaciones

- La separación en 4 módulos core (`telemetry.ts`, `telemetry-events.ts`, `telemetry-identity.ts`, `telemetry-buffer.ts`) resultó natural y facilitó el testing individual.
- 10 tests cubren identidad, firma criptográfica, eventos, buffer y configuración sin necesidad de red.
- El patrón best-effort (try/catch silencioso en todas las funciones públicas) es simple pero efectivo para telemetría que no debe afectar la operación principal.
