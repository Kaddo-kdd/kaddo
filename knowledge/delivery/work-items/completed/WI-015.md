# WI-015 — Agregar consentimiento interactivo y reversible para telemetría

## Intent

### Actor

Usuario de Kaddo que aún no ha tomado una decisión sobre telemetría.

### Problema

La telemetría implementada en WI-014 usa un modelo binario (`enabled: true/false`) que permanece deshabilitada por defecto. Muchos usuarios nunca descubren la capacidad y nunca toman una decisión explícita. Se necesita un modelo de consentimiento de tres estados con prompt interactivo de primera vez.

## Acceptance criteria

- [x] AC-01: Three-state Consent — Kaddo distingue `unset`, `enabled`, `disabled`
- [x] AC-02: First Interactive Use — proyecto con `consent = unset` solicita consentimiento
- [x] AC-03: Ask Once — después de elegir, no vuelve a solicitar
- [x] AC-04: Explicit Opt-in — telemetría solo opera con `consent = enabled`
- [x] AC-05: Disable Is Persistent — rechazo persiste y no muestra más prompts
- [x] AC-06: Re-enable — `kaddo telemetry enable` permite reactivar
- [x] AC-07: Identity Continuity — disable/enable conserva la identidad existente
- [x] AC-08: Existing Projects — migración compatible de config legacy
- [x] AC-09: Non-interactive Safety — CI, scripts, MCP nunca reciben prompts
- [x] AC-10: Centralized Integration — consent check como `preAction` hook compartido
- [x] AC-11: Telemetry Commands — `status/enable/disable` no provocan prompt automático
- [x] AC-12: Status Visibility — `kaddo telemetry status` muestra consent/registered/pending
- [x] AC-13: Privacy — ningún request antes de consentimiento `enabled`
- [x] AC-14: Documentation — docs EN/ES actualizadas con modelo de consentimiento

## Out of scope

- Cambios al Telemetry Service
- Analytics dashboard
- Nuevos eventos de producto
- Tracking de rechazos
- consentVersion re-prompt avanzado

## Evidence

### AC-01: Three-state Consent
- `telemetry-consent.ts` define `ConsentState = 'unset' | 'enabled' | 'disabled'`
- `getConsentState()` evalúa: consent field → legacy enabled field → unset
- Tests verifican los tres estados

### AC-02 + AC-03: First Interactive Use / Ask Once
- `ensureTelemetryConsent()` chequea `getConsentState()` → si `unset` + TTY interactivo → prompt con `@clack/prompts`
- `persistConsent()` escribe `consent` + `consentVersion` y elimina `enabled` legacy
- Post-consent: `getConsentState()` retorna `enabled` o `disabled` → no vuelve a preguntar

### AC-04 + AC-13: Explicit Opt-in / Privacy
- `isEnabled()` ahora usa `getConsentState(config) === 'enabled'`
- `unset` → `isEnabled()` retorna `false` → no hay requests

### AC-08: Existing Projects
- `getConsentState()` fallback: `enabled:true` → `'enabled'`, `enabled:false` → `'disabled'`, absent → `'unset'`
- Tests verifican los tres escenarios de migración

### AC-09: Non-interactive Safety
- `isInteractive()` retorna `false` si: `process.env.CI`, `!stdin.isTTY`, `!stdout.isTTY`
- `ensureTelemetryConsent()` retorna sin preguntar si no es interactivo
- Test verifica `CI=true` → `isInteractive() === false`

### AC-10: Centralized Integration
- `preAction` hook en `index.ts` llama `ensureTelemetryConsent()` para todos los comandos
- Skip para `telemetry status/enable/disable`
- `try/catch` envuelve todo para nunca bloquear un comando

### AC-11: Telemetry Commands
- `CONSENT_SKIP_COMMANDS` set excluye `status`, `enable`, `disable`
- `preAction` verifica `parent === 'telemetry'` antes de skip

### AC-12: Status Visibility
- `TelemetryStatus` incluye `consent: ConsentState`
- `runTelemetryStatus()` muestra `Consent: unset/enabled/disabled`

### AC-07: Identity Continuity
- `persistConsent()` solo modifica la sección `telemetry` del config
- Test verifica que `installationId` se preserva tras disable/enable

## Learning

### Decisiones de diseño

1. **Módulo separado `telemetry-consent.ts`:** Separar la lógica de consentimiento del cliente de telemetría permite testear el modelo de estados sin dependencias de red. El módulo es puro (no cwd, no logging).

2. **`preAction` para consent, `postAction` para events:** Commander.js soporta ambos hooks. El consentimiento debe evaluarse antes del comando para que el prompt sea visible; los eventos se emiten después. Esta separación es natural.

3. **Migración implícita sin reescritura:** `getConsentState()` interpreta `enabled:true/false` como legacy y los mapea a `enabled`/`disabled`. Solo cuando el usuario ejecuta `enable`/`disable` o acepta/rechaza el prompt se escribe el nuevo formato (`consent` + `consentVersion`). Esto evita tocar configs existentes innecesariamente.

4. **`delete prev.enabled` en `persistConsent`:** Al escribir `consent`, se elimina el campo `enabled` legacy para evitar ambigüedad. El campo `consent` tiene precedencia pero limpiar el legacy es más higiénico.

5. **`initialValue: false` en el prompt:** El default del prompt es `No` (N mayúscula en `[y/N]`), lo que asegura que el silencio o Enter rápido no activa telemetría.

### Observaciones

- El modelo de tres estados es compatible hacia atrás sin migración explícita: `getConsentState()` hace la traducción en runtime.
- 13 tests nuevos cubren: los tres estados, migración legacy, persistencia, re-enable, preservación de identidad, y detección de CI.
- El `preAction` hook no interrumpe `kaddo init` porque `loadConfig()` retorna `null` antes de que exista `.kaddo/config.yml`, y el hook retorna sin preguntar.
