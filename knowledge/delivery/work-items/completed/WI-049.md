# Deprecation CLI + MCP surfaces

Slice **C** de la épica [[WI-046]] (Controlled Deprecation). Depende de [[WI-047]] y [[WI-048]].

## Intent

Exponer el Deprecation Plan y los Targets por CLI y MCP, con mutaciones seguras (proposal → preview →
confirmación humana → Core), de modo que CLI/MCP/Admin converjan en el mismo Core.

## Scope

- **CLI**: `kaddo deprecation create | list | show | analyze | plan | status <DEP>` (naming final a
  afinar en handoff). Lectura rica; mutaciones con preview.
- **MCP**: tools para leer el plan, proponer candidatos, add/update target (confirm ausente/false →
  preview; confirm=true → apply), preparar análisis, inspeccionar dependencias/estado.
- Contrato de mutación `deprecation-write` espejando `resource-write.ts` (no-lossy, atomicWrite,
  nextDepId, buildFrontmatter).

## Acceptance criteria

- [x] CLI cubre create/list/show/analyze/plan/status con salida legible.
- [x] MCP: mutación de target exige confirmación (preview sin confirm, apply con confirm=true).
- [x] Ninguna mutación destructiva se aplica sin preview+confirm.
- [x] Tests CLI + MCP (preview vs apply, errores tipados).

## Validation

- `pnpm --filter @kaddo/cli test deprecation-write`: ids secuenciales DEP/DEP-TGT, duplicados y
  NOT_FOUND tipados, update no-lossy (preserva claves desconocidas), remove preview→confirm.
- `pnpm --filter @kaddo/mcp test` (deprecation-mutations): create/add-target/update-target/
  remove-target con preview sin confirm (no escribe) y apply con confirm=true; plan/analyze; fallos
  claros para plan inexistente y validación.
- Smoke CLI: `kaddo deprecation create|add-target|plan|status` sobre un proyecto temporal.
- Suites completas cli + mcp sin regresiones.

## Entry points

- `packages/cli/src/commands/resources.ts` — molde de comandos.
- `packages/cli/src/core/resource-write.ts` — patrón de mutación.
- `packages/mcp/src/tools.ts` + `server.ts` — registro de tools y patrón confirm/preview.

## Out of scope

Modelo (A), discovery/waves (B), integración WI/Resource (D), soft/observación (E), runbooks (F),
Admin (G).

## Learning

El contrato de mutación `deprecation-write.ts` espejó `resource-write.ts` casi línea por línea
(atomicWrite, serialize, nextId, buildFrontmatter, errores tipados, preview→confirm en el borrado), y
la superficie MCP reusó el patrón `needs_confirmation`/apply de las tools de recursos. Reutilizar el
molde probado hizo que CLI y MCP convergieran en Core sin inventar nada.

El hallazgo importante fue un **bug latente de caché de `gray-matter`**: `matter()` memoiza el parseo
por string de entrada, así que dos artifacts con contenido byte-idéntico comparten el MISMO objeto
`data`. `addTarget`/`updateTarget`/`removeTarget` mutaban `parsed.data` en el sitio
(`data.targets = …`), lo que envenenaba la caché y hacía aparecer targets de un plan en otro. Se
manifestó solo en los tests (planes con título idéntico "P") pero es un riesgo real en producción si
dos planes coinciden en contenido. La causa raíz: `resource-write.ts` nunca muta `parsed.data` porque
siempre lo clona con spread en `buildFrontmatter({...base})`; mi código no. Fix: clonar en
`loadPlanRaw` (`{ ...(parsed.data ?? {}) }`). Lección: **nunca mutar el objeto que devuelve
`gray-matter`; clonar antes de escribir.** Vale la pena auditar otros módulos de escritura por el mismo
patrón.

Nota de proceso: correr los tests del paquete MCP requiere lanzarlos desde la raíz del repo
(`npx vitest run packages/mcp/tests`); el `pnpm --filter @kaddo/mcp test` no halla archivos por el glob
`packages/**/tests/**` del config raíz cuando el cwd es el paquete — quirk pre-existente del repo.
