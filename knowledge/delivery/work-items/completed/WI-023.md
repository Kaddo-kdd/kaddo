# WI-023 — Implementar blog técnico de Kaddo para contenido editorial y SEO

## Intent

### Actor

Persona que llega a Kaddo desde buscadores, enlaces externos, comunidades técnicas o motores de búsqueda asistidos por IA y quiere aprender sobre Knowledge-Driven Development, desarrollo asistido por IA, agentes, arquitectura de software y sistemas legacy/brownfield.

### Problema

El sitio (`kaddo.org`) está orientado a documentación de producto. Funciona para quien ya conoce Kaddo, pero limita publicar contenido editorial que posicione en buscadores y atraiga a quien aún no conoce el proyecto. Falta una sección de blog nativa, versionada en el repo, optimizada para SEO y enlazada con la documentación.

### Goal

Separar dos intenciones: **Documentation** ("conozco Kaddo, ¿cómo lo uso?") y **Blog** ("estoy investigando un problema/concepto"). El blog es capa de adquisición; la documentación sigue siendo capa de producto.

```text
Search / LLM / Social → Technical Article → Concept → KDD → Kaddo Capability → Docs → Try/Install
```

## Technical direction

Stack verificado (2026-10-04): Astro `^5.5.0`, Starlight `^0.32.0`, `site: 'https://kaddo.org'`, i18n `defaultLocale: root` (EN en `/`, ES en `/es/`), `content.config.ts` con una sola colección `docs` (loader de Starlight). Implementar el blog con **capacidades nativas de Astro** — content collection (glob loader) + rutas Astro + layout propio de Kaddo. **No** introducir `starlight-blog` ni actualizar Astro/Starlight. Docs (Starlight) y Blog (Astro) comparten dominio, repo, deployment, branding, navegación y fundamentos SEO.

## Scope

1. **Blog content collection** (`content.config.ts`): colección `blog` tipada con glob loader, sin alterar `docs`. Artículos en Markdown/MDX versionados bajo `apps/docs/src/content/blog/`.
2. **Schema**: `title, description, publishedAt, updatedAt?, author, tags, locale (en|es), cover?, draft (default false), featured (default false)`. Campos extra solo si hay necesidad concreta.
3. **Rutas**: `/blog/`, `/blog/<slug>/`, `/es/blog/`, `/es/blog/<slug>/`. Slugs estables, legibles, SEO-friendly, independientes de la fecha.
4. **Blog index** (`/blog/` y `/es/blog/`): H1, descripción SEO, destacados, últimos, fecha, tags, resumen, cover cuando exista.
5. **Article layout** reutilizable: título, lead, autor, fecha publicación/actualización, cover, cuerpo, tags, links a docs relacionadas. Reutiliza identidad visual de Kaddo (no replica Starlight exactamente).
6. **Navegación principal**: acceso visible a **Blog** (Docs · Blog · GitHub). No agregar artículos a la sidebar de docs.
7. **SEO metadata** por artículo: `<title>`, meta description, canonical (`kaddo.org`), Open Graph, Twitter Card, author, published/modified date, cover. Sin canonicals a rutas viejas ni a `kaddo.trycatch.tv`.
8. **Structured data**: JSON-LD `BlogPosting`/`Article` (headline, description, author, datePublished, dateModified, image, mainEntityOfPage, publisher). Sin duplicar/contradecir el JSON-LD global (Person) existente en `astro.config.mjs`.
9. **Sitemap**: artículos publicados en el sitemap existente con `kaddo.org`; excluir drafts, rutas dev y locales inválidos.
10. **RSS**: `/blog/rss.xml` (evaluar `/es/blog/rss.xml` en Handoff). Solo publicados. (Añadir `@astrojs/rss` — adición compatible, no upgrade de framework.)
11. **Tags**: clasificación + páginas por tag (`/blog/tags/<tag>/`) cuando sea razonablemente simple; sin páginas vacías.
12. **Internal linking**: artículos enlazan a docs (`/knowledge-driven-development/`, `/use-cases/legacy-project/`, `/knowledge-capsules/`, `/getting-started/`). El blog explica el problema/concepto; los docs, cómo Kaddo lo resuelve.
13. **Related content**: derivado de tags (determinístico, sin IA): artículos relacionados + docs relacionadas.
14. **Bilingüe**: EN y ES; una publicación NO requiere traducción para publicarse. Cuando existan ambas, generar `hreflang` solo si se puede determinar equivalencia (no alternates falsos por compartir slug).
15. **Drafts** (`draft: true`): fuera de producción, index, tags, RSS, sitemap, related. Usables en dev local.
16. **Author**: soportar info de autor (primario `Julian Dario Luna Patiño`) sin hardcodear el layout de forma que impida autores adicionales; participa en metadata visible, structured data y SEO.
17. **Initial content**: al menos un artículo técnico real (no Lorem Ipsum) que valide routing, render, SEO, structured data, cover, tags, RSS, sitemap, internal links y locale.

## Out of scope

Upgrade mayor de Astro/Starlight; `starlight-blog`; CMS externo/headless; base de datos; editor web; comentarios; newsletter; analytics del blog; search externo; artículos generados por IA; traducción automática; estrategia SEO completa / keyword research; rediseño del sitio; migración de documentación. Tampoco la producción del catálogo editorial (clusters KDD / AI-assisted / Legacy-Brownfield / Architecture).

## Notas de Handoff (a definir en implementation-planning)

- **Rutas custom vs Starlight:** Starlight controla las rutas de docs vía su integración; las páginas Astro bajo `src/pages/blog/**` y `src/pages/es/blog/**` coexisten y renderizan con layout propio. Confirmar que Starlight no intercepta `/blog/`.
- **Navegación "Blog":** Starlight 0.32 no expone links de header arbitrarios por config; probablemente requiera override del componente Header/SiteTitle de Starlight, o inyección vía `head`/componente. Definir el mecanismo menos invasivo.
- **Sitemap:** Starlight ya configura `@astrojs/sitemap` (el build emite `sitemap-index.xml`); confirmar que incluye las páginas Astro del blog y excluye drafts (los drafts no deben generar página).
- **Layout reuse:** reutilizar tokens de `src/styles/brand.css`; fuentes (Inter/Poppins) ya cargadas por Starlight sólo aplican en páginas Starlight — el layout del blog debe cargarlas también.
- **hreflang / canonical:** componer sin contradecir el JSON-LD Person global ni los metas author existentes en `astro.config.mjs`.
- **RSS:** `@astrojs/rss` como dependencia nueva (adición compatible con Astro 5).

## Learning

### Decisiones de diseño

1. **Blog nativo Astro junto a Starlight, no `starlight-blog`:** El blog usa content collection + rutas Astro con layout propio, que conviven con Starlight sin que este intercepte `/blog/`. Evita forzar un upgrade de Astro/Starlight (el riesgo que el spec quería esquivar).

2. **RSS hand-rolled en vez de `@astrojs/rss`:** Un endpoint que emite RSS 2.0 válido evita agregar una dependencia (y cualquier fricción de instalación/compatibilidad), cumpliendo AC-11 con el espíritu de "sin deps innecesarias". `getPosts` ya excluye drafts, así que el feed queda limpio.

3. **Locale por subcarpeta (`en/`, `es/`), no sufijo `.es`:** El glob loader de Astro **slugifica** el id y elimina el punto, así que `foo.es.md` producía el slug roto `fooes` (detectado en el primer build). Con subcarpetas, EN y ES comparten exactamente el mismo slug base → el `hreflang` los relaciona correctamente. Se documentó la convención para autores.

4. **Nav "Blog" vía override de `SocialIcons`:** Starlight 0.32 no expone links de header arbitrarios; `SocialIcons` es el punto de override documentado que reusa el default y añade el link, sin reimplementar el Header.

5. **Fechas en UTC:** `publishedAt: YYYY-MM-DD` parsea como medianoche UTC; formatear en timezone local mostraba el día anterior. `Intl.DateTimeFormat` con `timeZone: 'UTC'` lo corrige.
