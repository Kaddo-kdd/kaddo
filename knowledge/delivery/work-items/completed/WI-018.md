# WI-018 — Initiative Core: artifact, lifecycle, roadmap materialization y progreso

> Hijo de [WI-017](./WI-017.md) (epic). Cubre las fases 1-3 del Handoff del epic: Core, Roadmap & Candidates, Progress. Es la base de datos/lógica sobre la que se construyen WI-019/020/021.

## Intent

### Problema

Hoy la Initiative no existe como entidad. El roadmap genera `RM-xxx` y `WI-CANDIDATE-xxx`, `kaddo create --from roadmap` materializa WIs con provenance, y el read model de WI ya expone `initiative: string | null` ([work-items.ts:51](packages/cli/src/core/work-items.ts:51)). Falta la capa de Core que represente una Initiative como artifact operable con lifecycle y progreso calculado.

### Goal

Implementar en Core (`packages/cli`) la Initiative como artifact first-class, su lifecycle, la materialización desde roadmap, los candidates bajo una Initiative, y el cálculo de progreso (planning + delivery) — todo como lógica pura testeable, sin superficies CLI/MCP/Admin todavía.

## Scope

- Artifact `knowledge/delivery/initiatives/INI-xxx-*.md` con frontmatter (`type: initiative`, `id`, `title`, `status`, `horizon`, `priority`, `knowledge_level`, `domains`, `related_capabilities`, `source`, `source_id`, `created_at`, `external_links`).
- Parser / read model de Initiative (análogo a work-items read model).
- Generación de IDs `INI-xxx` deterministas y collision-safe.
- Lifecycle: `candidate → planned → in-progress → completed` + `deferred`/`cancelled`. Transiciones puras validadas.
- Relación opcional WI↔INI: resolver `INI-001 → [WI-021, WI-022, …]` consultando artifacts (sin lista manual paralela). El campo `initiative` del WI es la fuente.
- Materialización `RM-001 → INI-001` preservando `source: roadmap`, `source_id: RM-001`.
- Candidates bajo Initiative (id, title, type, suggested knowledge level, expected value, notes, source signals, dependencies, materialization status/reference).
- Materialización `WI-CANDIDATE-001 → WI-021` conservando la relación.
- Progreso: planning coverage (materializados/totales) y delivery progress (conteo por estado de WIs asociados), sin porcentaje arbitrario.

## Out of scope

- Comandos CLI, tools MCP, Admin (WI-019/020/021).
- `initiative-agent`, gap analysis, completion readiness analysis (WI-020).
- external_links consumo/asociación de imports (WI-021), aunque el campo se define aquí.
- Grafo (WI-021).

## Learning

### Decisiones de diseño

1. **Separación read/write (`initiative.ts` vs `initiative-write.ts`):** Refleja la convención existente del repo (`work-items.ts` vs `work-item-write.ts`). Permite testear el modelo y el progreso sin tocar escritura, y mantiene las escrituras aisladas.

2. **Asociación WI→INI por metadata `initiative: INI-xxx`, resuelta en runtime:** No se mantiene una segunda lista en el artifact de Initiative; `associatedWorkItems` consulta los WIs y filtra por el campo `initiative`. Evita desincronización (una sola fuente de verdad). El match es por id, exacto y case-insensitive.

3. **Planning y delivery separados, sin porcentaje único:** `computeInitiativeProgress` devuelve `planning` (candidates materializados/total) y `delivery` (conteo por estado de lifecycle) como dimensiones distintas, respetando el principio del epic de no asumir pesos iguales ni inventar un % arbitrario.

4. **Candidate materializado marca `materialized_as` en el artifact:** Al materializar un candidate se escribe el WI id de vuelta en el candidate, de modo que planning coverage es derivable del propio artifact sin estado externo.

### Bug encontrado (y arreglado)

5. **gray-matter cachea `matter(content)` por string:** La librería cachea el resultado del parseo cuando se la llama sin opciones, y devuelve el **mismo objeto** para contenidos idénticos. Como los write-paths mutaban ese `data` (p. ej. `data.status = ...`), dos Initiatives byte-idénticas compartían y corrompían una única entrada de cache — un test leía el estado de otra. Se evitó pasando `{}` como opciones en los `matter()` de parseo (`initiative.ts`, `initiative-write.ts`). Es un riesgo real más allá de tests: dos artifacts con el mismo contenido en un mismo proceso se habrían pisado. El resto del repo no lo había visto porque los WIs nunca son byte-idénticos (ids/títulos distintos).

### Observaciones

- El campo `initiative` ya existía en el read model de WI y en `artifact-reader` antes de este WI, así que AC-04 partió de una base existente; lo nuevo es la resolución inversa y el artifact INI.
- Las superficies CLI/MCP/Admin quedan para WI-019/020; este WI es solo Core, consumible vía `@kaddo/cli/core`.
