# WI-024 — Soportar diagramas Mermaid en conocimiento de negocio, producto y tecnología

## Intent

### Problema

El conocimiento de Kaddo para Business, Product y Tech se expresa principalmente en Markdown. Ciertos tipos de conocimiento se entienden mejor visualmente (actores y relaciones, flujos de negocio, journeys de producto, dependencias entre capacidades, contexto de sistemas, componentes, secuencias, integraciones, dependencias entre módulos). Hoy se puede escribir Mermaid dentro de Markdown, pero Kaddo no lo trata explícitamente como parte de sus definiciones ni garantiza su representación adecuada en las superficies. En particular, el Admin muestra los bloques Mermaid como código en lugar de renderizarlos.

### Goal

Permitir que las definiciones de Business, Product y Tech incluyan diagramas Mermaid como parte natural del conocimiento, con **una sola fuente de verdad** (Markdown):

```text
Knowledge Markdown + ```mermaid ... ```
      ↓ misma fuente
CLI / MCP → el source Mermaid permanece como Markdown
Admin     → el source Mermaid se renderiza como diagrama
```

No crear un formato paralelo. Markdown sigue siendo canónico.

## Product principle — Diagram as Knowledge

Un diagrama no es una imagen decorativa ni un artifact independiente: es conocimiento versionable (Markdown + Mermaid source + Git). Así humanos lo leen, los LLMs lo entienden, Git lo diffea, el Admin lo renderiza y el conocimiento sigue siendo portable.

## Scope (secciones del spec)

1. **Capas soportadas**: Mermaid explícito en Business, Product y Tech. Cubrir al menos `business/business.md`, `product/product.md`, `tech/codebase.md`, `tech/current-state.md`. El renderer del Admin debe funcionar para cualquier artifact Markdown de Knowledge con bloques Mermaid (no hardcodear por filename).
2. **Business diagrams**: actores, contexto de negocio, value flows, procesos, participantes externos, dependencias high-level.
3. **Product diagrams**: user/product flows, relaciones de capabilities, interacción de features, lifecycle, actor → capability → outcome.
4. **Tech diagrams**: system context, componentes, módulos, dependencias, integraciones, data flows, secuencias, deployment. Tipos útiles: `flowchart`, `sequenceDiagram`, `classDiagram`, `stateDiagram-v2` (no restringir técnicamente si el renderer soporta otros de forma segura).
5. **Templates**: actualizar templates de Business/Product/Tech para indicar que pueden incluir una sección visual (`## Diagrams`, con guía). No generar diagramas vacíos/artificiales solo por completar el template.
6. **Agent guidance**: actualizar agentes (`business-agent`, `product-agent`, `capability-agent`, `codebase-agent`, `architecture-agent`) para considerar Mermaid durante refinement. Regla: usar Mermaid cuando mejore materialmente la comprensión; no crear diagrama solo porque exista la sección; no inventar entidades/relaciones.
7. **Consistencia texto/diagrama**: el diagrama no debe introducir hechos no soportados por el conocimiento; texto y diagrama deben representar el mismo estado conocido.
8. **Mermaid como source Markdown**: no almacenar PNG/SVG/screenshots/base64/DB de diagramas como representación canónica; el source permanece como bloque ```mermaid```. Los outputs visuales son derivados.
9. **Admin rendering**: el Admin detecta bloques ```mermaid``` en el detalle de Knowledge y los renderiza visualmente, dentro de la vista normal (no una segunda vista separada).
10. **Render genérico**: implementado sobre el renderer de Markdown existente (handler de code-block), no con condiciones por filename. Futuros artifacts se benefician automáticamente.
11. **Seguridad del render**: configuración segura (securityLevel restrictivo de Mermaid); no ejecutar JavaScript arbitrario; no `dangerouslySetInnerHTML` con contenido no controlado sin sanitización/garantías equivalentes.
12. **Mermaid inválido**: no debe romper la página/ruta/app. El Markdown y los demás diagramas siguen visibles; el bloque inválido muestra un error local no bloqueante o cae al source. El usuario identifica qué bloque falló.
13. **Múltiples diagramas**: un artifact puede tener varios; se renderizan independientemente; el fallo de uno no impide los demás.
14. **Responsive**: legible en desktop/tablet/mobile; diagramas grandes con overflow horizontal o fit-to-container sin romper el layout. (Sin editor gráfico/zoom avanzado/canvas en este WI.)
15. **Theme**: legible con los themes del Admin (light/dark); configuración Mermaid apropiada al theme; no hardcodear colores que contradigan el theme salvo que vengan en el source.
16. **CLI**: sin parsing destructivo de Mermaid; los comandos que leen/ensamblan Knowledge preservan los bloques. Sin render en terminal.
17. **MCP**: sigue entregando el artifact como Markdown incluyendo el source Mermaid. Sin tool específico de diagramas en este WI.
18. **Bootstrap/proyectos existentes**: backward-compatible; proyectos sin Mermaid siguen igual; sin migración forzada de los artifacts existentes.

## Out of scope

Editor Mermaid visual; drag-and-drop; DB de diagramas; canvas editable; persistencia automática PNG/SVG; versionado de diagramas separado de Git; generación automática sin razonamiento agente/humano; diagram-to-code; reverse engineering de código a Mermaid; editor de topología interactivo; reemplazar el Knowledge Graph existente; render de Mermaid en CLI; protocolo MCP específico de diagramas.

## Learning

### Decisiones de diseño

1. **Extender el handler de `code` del renderer existente, no un parser aparte (AC-08):** El Admin ya usaba `react-markdown` con un componente custom para `code`. Añadir una rama `className === 'language-mermaid'` → `<MermaidDiagram>` cubre AC-07/08/10 de una, es genérico (cualquier artifact Markdown con mermaid se beneficia) y no toca el pipeline de sanitización del resto del Markdown.

2. **`securityLevel: 'strict'` como garantía para el `dangerouslySetInnerHTML` (AC-11):** El SVG se inyecta con `dangerouslySetInnerHTML`, pero proviene de `mermaid.render` en modo estricto (Mermaid sanitiza su propio output, sin scripts ni handlers) y el source viene del propio Knowledge del proyecto, no de HTML de usuario. Es el patrón documentado de Mermaid; se dejó comentado en el código.

3. **Fallback por bloque, no global (AC-10/12):** Cada `<MermaidDiagram>` captura su propio error de `render` y cae a mostrar el source. Así un diagrama inválido no rompe la página ni los demás diagramas, y el usuario ve qué bloque falló.

4. **Guía de templates en prosa, sin diagrama de ejemplo (AC-05):** La primera versión incluía un `flowchart` de ejemplo en el template, lo que habría sembrado diagramas genéricos en cada archivo scaffoldeado. Se quitó: la sección `## Diagrams` es solo guía; el ejemplo vive en la documentación.

5. **Preservación es inherente, pero se bloqueó con tests:** Ni CLI ni MCP tienen parsing de Mermaid; tratan Knowledge como texto. Los tests de preservación fijan ese contrato (AC-14/15) para evitar regresiones futuras.

### Observaciones

- Al dar `ready` el WI "no se encontraba": el frontmatter tenía dos errores de YAML (un glob `*ermaid*` que YAML lee como alias, y una razón con `dependencia:` sin comillas que YAML lee como mapping). Se corrigieron comillando. Lección: en frontmatter de WIs, comillar valores con `*` inicial o con `: ` interno.
- `mermaid` se code-splittea por tipo de diagrama en el bundle del Admin (sequenceDiagram, architectureDiagram, etc.), así que solo se carga lo usado.
- Las copias bundled `packages/cli/dist/admin-dist` y `admin-server` que sirve `kaddo admin` se regeneran con `pnpm -r build` en release; se refrescaron manualmente solo para la verificación local (son gitignored).
