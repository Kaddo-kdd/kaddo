# Deprecation Core Model: Plan + Targets + lifecycle + environment state

Slice **A** de la épica [[WI-046]] (Controlled Deprecation).

## Intent

Dar al Core de Kaddo el modelo de datos de la deprecación controlada: el **Deprecation Plan**
versionable y sus **Deprecation Targets** tipados, con lifecycle, estado por ambiente y assessments.
Es la base sobre la que se construyen Discovery (B), CLI/MCP (C), integración con WI/Resources (D),
soft deprecation (E), runbooks (F), Admin (G) y graph/docs (H).

## Scope

- Read model para `knowledge/legacy/deprecations/DEP-xxx-<slug>.md` (`type: deprecation-plan`):
  identidad, propósito, targets, orden/waves (derivadas, no escritas a mano), estado.
- **Deprecation Target** (`DEP-TGT-xxx`) tipado: module, route, function, ui, job, database-object,
  integration, config, other; con `locator` apropiado por tipo (ruta/símbolo/objeto DB, no "archivo").
- **Lifecycle** del target: candidate → usage-validated → soft-deprecated → disabled → removed-devtest
  → production-ready → production-changed → observing → completed; + estado terminal
  `deprecated-retained`.
- **Environment-aware state**: estado por ambiente (development/test/production) separado del estado
  global; no permitir `removed` global con producción activa.
- **Assessments** (campos): `unused_confidence`, `blast_radius`, `reversibility` (orientativos).
- Tipos TS exportados desde `core.ts` para consumo de CLI/MCP/Admin.

## Acceptance criteria

- [x] Core parsea/serializa `DEP-xxx` bajo `knowledge/legacy/deprecations/` (cubre AC-01).
- [x] Targets tipados con locators correctos por tipo (cubre AC-02).
- [x] Estado por ambiente Dev/Test/Production separado del estado global (cubre AC-08).
- [x] Un target puede quedar en `deprecated-retained` (cubre AC-13).
- [x] Tests de Core (parse/serialize round-trip, lifecycle inválido rechazado, env-state independiente).

## Validation

- `pnpm --filter @kaddo/cli test` sobre un nuevo `deprecation.test.ts`:
  - round-trip parse→serialize de un `DEP-xxx` canónico (sin pérdida).
  - target de cada tipo (module/route/function/ui/job/database-object/integration/config/other) con su
    locator; locator inválido para el tipo → error tipado.
  - transición de lifecycle inválida rechazada; `deprecated-retained` aceptado como terminal.
  - environment-state Dev/Test/Production independiente del estado global; `removed` global con
    producción activa → rechazado.
- `pnpm --filter @kaddo/cli test` (suite completa) sin regresiones (el modelo es aditivo).

## Learning

El Core Model se construyó espejando el patrón ya probado de `resources.ts` (read model vía
`discoverKnowledge` + `gray-matter`) en lugar de inventar un subsistema nuevo: `knowledge/legacy/
deprecations/` se escanea recursivamente sin tocar `knowledge-artifacts.ts`, basta con que el artifact
declare `type: deprecation-plan`. Los targets viven embebidos en el frontmatter del plan (`targets:`),
no como archivos sueltos: mantiene "un plan = un archivo", hace derivables los conteos/waves y evita un
segundo mecanismo de discovery.

Dos decisiones de diseño reforzaron los principios de seguridad del épica directamente en el modelo:
(1) **estado por ambiente independiente del lifecycle global** — `validateTarget` rechaza `completed`
o `production-changed`/`observing` mientras un ambiente siga `active`, de modo que un retiro en Dev/Test
nunca se confunde con un cambio de producción; (2) **unknown se preserva como unknown** — los
assessments ausentes quedan `null`, nunca se fabrican como `none`/`unused`, materializando
"absence-of-reference ≠ unused" a nivel de parseo. Las transiciones de lifecycle son un mapa explícito
(`candidate` no puede saltar a `removed-devtest`), y `deprecated-retained` es terminal y válido con
producción activa (retención obligatoria).

Nota de proceso: `kaddo ready` y `kaddo learn` son interactivos (requieren TTY) y fallan en un entorno
no interactivo; `ready` admite `--yes`, pero `learn` no, así que el cierre se hizo replicando su
transformación canónica (status→completed, `completed_at`, sección Learning, mover a `completed/`). La
transición ready→in-progress no está en `transitionWorkItem` (solo draft↔ready); la hace normalmente el
handoff MCP, y aquí se replicó el mismo efecto canónico (status + carpeta). Candidato de mejora:
exponer `--yes` en `learn` y una transición CLI a in-progress para flujos headless/agénticos.
