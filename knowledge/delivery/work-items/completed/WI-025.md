# WI-025 — Mejorar la representación de Work Items en Admin preservando la definición Markdown completa

## Intent

### Problema

El Admin presenta los Work Items mediante una **proyección estructurada** construida por Core
(`WorkItemDetail`). Esa proyección muestra de forma útil lifecycle, captured intent, actor/outcome,
current/target behavior, scope, scope confidence, affected modules, system impact, module coverage,
impact analysis, acceptance criteria, decisions/knowledge, implementation evidence, release gates,
completion exceptions y provenance.

Pero el Work Item canónico es un **artifact Markdown** que puede contener secciones válidas que
`WorkItemDetail` no modela (`Problem`, `Goal`, `Expected Value`, `Dependencies`, `Design`, `Risks`,
`Out of Scope`, `Validation`, `Definition of Done`, `Implementation Handoff Guidance`, `Learning`,
`Notes`, y secciones futuras). Core sólo proyecta los headings que su parser reconoce
(`splitSections` + `sectionText`/`sectionBullets`); el resto desaparece de la vista.

```text
Canonical Work Item Markdown  →  contiene X  →  Admin structured projection  →  X desaparece
```

El Admin no debe dar la impresión de mostrar la definición completa cuando parte del artifact
canónico queda omitida.

### Goal

Que un usuario pueda consultar desde el Admin **toda la definición significativa** de un Work Item,
sin perder las ventajas de la vista estructurada.

```text
Canonical WI Markdown
        ↓ Core
 ┌──────┴────────┐
Structured View   Full Definition
 (UI optimizada)  (Markdown renderizado)
 └──────┬────────┘
        ↓ Admin
```

## Product principle — Structured projection ≠ source of truth

El Admin puede interpretar y presentar el WI de forma estructurada, pero **no** debe reemplazar
silenciosamente el artifact Markdown:

- Work Item Markdown = definición canónica.
- Vista estructurada del Admin = proyección.
- Vista Markdown completa = representación fiel.

## Actor y outcome

- **Actor**: una persona (dev, PM, ownership) que abre el detalle de un Work Item en el Admin.
- **Outcome observable**: desde el detalle del WI puede ver toda sección Markdown presente en el
  artifact canónico (incluyendo `Validation`, `Definition of Done`, `Learning`, `Out of Scope`,
  `Risks`, `Design` y secciones futuras), además de la vista estructurada existente, sin pérdida de
  información y sin que una sección quede inaccesible.

## Current behavior

```text
Markdown WI → Core parser (splitSections) → WorkItemDetail { outcome, scope, acceptanceCriteria,
evidence, releaseGates, ... } → Admin
```

`getWorkItem` (en `packages/cli/src/core/work-items.ts`) **ya** lee el cuerpo completo del artifact
con `readBody(match.filePath)`, pero sólo expone los headings reconocidos. Las secciones no
reconocidas no llegan a `WorkItemDetail` y por tanto no se muestran en `WorkItemDetail.tsx`.

## Target behavior

La vista de detalle conserva **dos niveles de lectura**:

1. **Structured Overview** — la representación actual para información operacional: Status,
   Refinement, Delivery status, Outcome, Scope, Scope confidence, System impact, Module coverage,
   Acceptance criteria, Decisions, Evidence, Release gates, Provenance.
2. **Full Definition** — el cuerpo Markdown canónico completo, renderizado con el `MarkdownRenderer`
   existente. Se integra en la misma página (p. ej. tabs `Overview` / `Full definition`, o una
   sección "Definition" con la definición completa accesible con una sola acción). La decisión
   visual exacta se define en Handoff.

## Entry points (grounding técnico)

- `packages/cli/src/core/work-items.ts` — añadir `markdownBody: string` a `WorkItemDetail` y
  asignarlo en `getWorkItem` desde el `body` ya leído (sin reconstruir desde la proyección).
- `packages/admin-server/src/contracts/schemas.ts` — añadir `markdownBody` al schema de respuesta
  del detalle de WI.
- `packages/admin-server/src/core-adapter.ts` — propagar el campo desde Core a la respuesta.
- `packages/admin/src/lib/api.ts` — añadir `markdownBody` al tipo `WorkItemDetail` del cliente.
- `packages/admin/src/routes/WorkItemDetail.tsx` — añadir la vista "Full definition" que renderiza
  `markdownBody` con `MarkdownRenderer`.
- `packages/admin/src/components/MarkdownRenderer.tsx` — se **reutiliza** (ya soporta headings,
  listas, tablas, code blocks, links y Mermaid); no se crea un renderer paralelo.

## Surface review

- **Backend / Core** (afectado): nuevo campo aditivo `markdownBody` en el read model.
- **API / Admin Server** (afectado): contrato + adapter propagan el campo.
- **Frontend / Admin** (afectado): nueva vista "Full definition" reutilizando el renderer.
- **Markdown renderer** (reutilizado, no modificado salvo que surja un gap): soporte existente.
- **Base de datos** (no aplica): no se persiste nada nuevo; Markdown sigue siendo la única fuente.
- **CLI / MCP** (no afectado): no cambian; el artifact ya es Markdown.
- **Auth, notifications, analytics** (no aplica).
- **Documentación** (revisado): opcional, menor; el comportamiento es visual en Admin.

## Scope

1. **Exponer el Markdown canónico**: Core entrega el cuerpo Markdown del artifact (posterior al
   frontmatter) como `markdownBody`, directamente desde el artifact, sin reconstruirlo.
2. **No duplicar la fuente**: no se crea un segundo archivo ni se persiste una representación
   paralela. `knowledge/delivery/work-items/.../WI-xxx.md` sigue siendo la única fuente de verdad.
3. **Renderizar en Admin con el renderer existente** (`MarkdownRenderer`): headings, listas, tablas,
   code blocks, links y Mermaid.
4. **Preservar la vista estructurada**: no reemplazarla por un dump de Markdown; complementa, no
   degrada.
5. **Evitar duplicación confusa**: cuando una sección ya aparece estructurada, la UI evita repetir
   la misma información de forma extensa una tras otra; la definición completa sigue accesible con
   una sola acción o dentro de la vista.
6. **Secciones desconocidas/futuras visibles**: cualquier heading nuevo y válido aparece
   automáticamente en Full Definition sin requerir una nueva feature.
7. **Metadata de frontmatter**: la vista estructurada sigue mostrando metadata significativa; en
   Handoff se revisa qué metadata canónica útil no se presenta hoy (p. ej. `initiative`,
   `knowledge_level`, `domains`, `affected_modules`, code globs, `dependencies`, source
   candidate/initiative, `created_at`, `ready_at`, `completed_at`) y se incorpora donde aporte
   trazabilidad. No se vuelca el YAML crudo.
8. **Trazabilidad de Initiative**: si el WI pertenece a una `initiative`, la relación es visible y,
   cuando sea posible, navegable al detalle de la Initiative.
9. **Provenance**: roadmap/initiative/WI candidate/external source se representa de forma coherente
   (responder "¿por qué existe este Work Item?").
10. **DoD & Validation**: `Validation` y `Definition of Done`, cuando existen, son accesibles desde
    Admin (vía Full Definition; no es obligatorio modelarlas como campos nuevos).
11. **Learning**: los WIs `completed` con `## Learning` permiten consultar ese aprendizaje desde
    Admin (es parte del Build Contract).

## Out of scope

Rediseñar completamente la pantalla de Work Items; convertir todos los headings Markdown en campos
de Core; crear un CMS para Work Items; editar Markdown raw desde Admin; cambiar el formato canónico
de los WI; migrar Work Items existentes; crear nuevas etapas del lifecycle; modificar el Build
Contract; reemplazar `MarkdownRenderer`; hacer cada sección Markdown editable independientemente.

## Acceptance criteria

- [x] AC-01 — Canonical Body: Core expone el cuerpo Markdown canónico del Work Item sin
  reconstruirlo desde la proyección estructurada.
- [x] AC-02 — No Information Loss: cualquier sección Markdown válida presente en el WI puede
  consultarse desde el Admin aunque Core no la modele explícitamente.
- [x] AC-03 — Structured View Preserved: la vista estructurada actual continúa disponible para
  lifecycle, scope, impact, evidence, verification y provenance.
- [x] AC-04 — Full Definition: el detalle del WI ofrece una representación claramente accesible de
  la definición Markdown completa.
- [x] AC-05 — Shared Renderer: la definición usa el `MarkdownRenderer` existente en Admin y no un
  renderer paralelo específico para WI.
- [x] AC-06 — Markdown Features: headings, lists, tables, code blocks, links y Mermaid siguen
  funcionando dentro de Work Items.
- [x] AC-07 — Future Sections: headings desconocidos o agregados en el futuro se muestran
  automáticamente en Full Definition.
- [x] AC-08 — DoD & Validation: `Validation` y `Definition of Done`, cuando existen, son visibles
  desde Admin.
- [x] AC-09 — Learning: `Learning` de WIs completed es visible desde Admin.
- [x] AC-10 — Out of Scope / Risks / Design: secciones no cubiertas por el read model siguen siendo
  consultables desde la definición completa.
- [x] AC-11 — Metadata Review: metadata relevante actualmente omitida se identifica en Handoff y se
  incorpora a la vista estructurada cuando aporte trazabilidad.
- [x] AC-12 — Initiative: la Initiative asociada, cuando exista, es visible y navegable desde el WI.
- [x] AC-13 — Provenance: roadmap candidate, initiative, external source u otro origen preservado
  por Core sigue siendo visible desde Admin.
- [x] AC-14 — Backward Compatibility: Work Items antiguos o con formatos parciales continúan
  cargando sin errores.
- [x] AC-15 — No Duplicate Source: no se crea ni persiste una segunda versión del Markdown para
  soportar la UI.

## Validation

- **Complete modern WI**: abrir un WI con `Intent`, `Problem`, `Goal`, `Current/Target Behavior`,
  `Scope`, `Out of Scope`, `Acceptance Criteria`, `Validation`, `Definition of Done`, `Risks`,
  `Learning` → Structured Overview muestra los campos especializados y Full Definition muestra todas
  las secciones del Markdown. Ninguna sección queda inaccesible.
- **Unknown section**: agregar temporalmente `## Rollout Strategy` → sin cambios en el parser de
  Core, Full Definition la muestra.
- **Mermaid**: incluir un bloque ```mermaid``` (p. ej. `flowchart LR; A --> B`) → se renderiza con
  el soporte Mermaid existente dentro de Full Definition.
- **Completed WI**: abrir un WI `completed` con `## Learning` → el aprendizaje es visible en Admin.
- **Legacy WI**: abrir un WI antiguo sin todas las secciones modernas → la proyección estructurada
  es tolerante, el Markdown completo es legible, sin fallo de render.
- **Regresión**: suites de CLI (Core), Admin Server y Admin sin regresiones.

## Definition of Done

- Core expone `markdownBody` canónico de un Work Item (desde el artifact, no reconstruido).
- Admin Server lo entrega sin transformaciones destructivas.
- Admin permite consultar la definición completa; la vista estructurada se conserva.
- Se reutiliza `MarkdownRenderer`; Mermaid y demás Markdown funcionan dentro de WIs.
- Secciones no modeladas dejan de quedar ocultas; `Validation`, `Definition of Done`, `Out of
  Scope` y `Learning` son consultables.
- Metadata relevante faltante se revisa y se incorpora donde aporte valor; Initiative y provenance
  visibles.
- Secciones futuras no requieren cambios de UI para ser visibles; WIs existentes siguen funcionando.
- Tests cubren Core, Admin Server y Admin; se valida visualmente en navegador con al menos un WI
  moderno y uno legacy.
- Implementation Evidence recolectada; Verification pasa; Learning documenta cualquier gap entre el
  artifact canónico y la proyección del Admin.

## Implementation handoff guidance

Antes de implementar, comparar explícitamente: (1) campos presentes en `WorkItemDetail`, (2)
secciones reales encontradas en WIs actuales, (3) información presentada por `WorkItemDetail.tsx`.
Construir una matriz temporal por cada pieza de información: ¿parsed por Core? ¿expuesta por API?
¿renderizada estructuralmente? ¿visible vía Full Definition?

Preferir `Canonical Markdown → Core markdownBody → Admin Server → Admin { Structured Overview, Full
Definition }` sobre `cada nuevo heading → nuevo parser → nuevo campo API → nuevo componente React`.
La segunda opción vuelve frágil al Admin frente a la evolución natural del formato de los WI.

## Learning

- **El cambio fue más pequeño de lo que el spec sugería.** `getWorkItem` ya leía el cuerpo
  completo (`readBody`); exponer `markdownBody` fue una línea en Core. El grueso del valor
  (sin pérdida de información) salió casi gratis reutilizando `MarkdownRenderer` (con Mermaid de
  WI-024). Confirma el principio del handoff: `Core markdownBody → Full Definition` en vez de
  "un heading nuevo → un parser → un campo → un componente".
- **Full Definition renderiza solo el cuerpo, no el frontmatter.** Por eso metadata que vive únicamente
  en el frontmatter (`knowledge_level`, `domains`, timestamps) no aparece en ninguna de las dos vistas.
  Para AC-11 se promovió la pieza de mayor trazabilidad —**Initiative** (AC-12), que Core ya exponía
  (`wi.initiative`) y con ruta `/initiatives/$initiativeId` ya existente— como enlace navegable en
  *Details*. Promover además `knowledge_level`/`domains`/timestamps se evaluó y se **difirió**:
  requeriría extender el read model tipado de Core por poco valor marginal y roza el "volcado de YAML"
  que este WI declara fuera de alcance. Candidato a un WI futuro si se pide trazabilidad más rica.
- **Gap artifact↔proyección confirmado y cerrado por diseño.** Antes, secciones como `Validation`,
  `Definition of Done`, `Risks` y `Learning` sólo se veían si Core modelaba su heading; ahora cualquier
  heading (incluido uno futuro como `Rollout Strategy`) es visible vía Full Definition sin tocar el parser.
- **Nota de proceso (import).** `kaddo work-item import` volcó el spec completo dentro del campo
  `summary:` del frontmatter y dejó el body casi vacío; hubo que reescribir el artifact a estructura
  canónica en refinement. Vale la pena revisar el importer para que el cuerpo Markdown largo caiga en
  el body, no en `summary`.
- **Nota de verificación.** `kaddo verify` atribuyó los 5 archivos cambiados al entity `core` de la
  topología semántica, de ahí el warning "planned: cli/admin-server/admin vs actual: core". Es cosmético
  (el mapeo entity↔package), no un problema de alcance; conviene alinear la atribución de evidencia con
  `.kaddo/modules.yml`.
