# Sincronizar el README de @kaddo/cli en npm con el README canónico del repositorio

## Intent

### Problema

Kaddo mantiene su README principal en `README.md` (la descripción más completa y actualizada en
GitHub). Pero `@kaddo/cli` se publica desde `packages/cli/` y su `package.json` incluye
`"files": ["dist", "README.md", "LICENSE"]`, así que npm usa `packages/cli/README.md` como README
del paquete publicado. Hoy ambos evolucionan de forma independiente (`packages/cli/README.md` tiene
559 líneas vs. 304 del raíz, con tagline y secciones distintas) y el release no sincroniza el README
del paquete antes de `npm publish` → **drift** entre lo que se ve en GitHub y lo que ve una persona
en `@kaddo/cli` en npm.

### Goal

`README.md` → generación determinística → `packages/cli/README.md` → `npm publish`, de modo que la
página de `@kaddo/cli` en npm siempre refleje la versión del README principal del commit/tag que se
publica.

## Product principle — One canonical project README

El README raíz es la fuente principal para explicar Kaddo. No mantener a mano dos documentos
equivalentes; `packages/cli/README.md` es una representación **derivada** para distribución npm.

## Actor y outcome

- **Actor**: una persona que descubre Kaddo en la página de `@kaddo/cli` en npm; y el maintainer que
  publica una release.
- **Outcome observable**: la página de npm de `@kaddo/cli` muestra el contenido del README raíz del
  commit publicado (assets y links que resuelven fuera del repo), y el maintainer no necesita
  recordar que existe una segunda copia — el release falla si el README derivado está desactualizado.

## Current behavior

```text
README.md              → GitHub (canónico, 304 líneas)
packages/cli/README.md → npm   (copia independiente, 559 líneas, stale)
release.yml            → checkout → install → build → test → verify versions → npm publish (cli, mcp)
```

No hay paso que sincronice ni valide `README.md ↔ packages/cli/README.md` antes del publish.

## Target behavior

```text
README.md → scripts/sync-npm-readme.mjs (transform determinístico) → packages/cli/README.md → npm
```

`pnpm npm-readme:sync` regenera; `pnpm npm-readme:check` valida drift sin mutar (exit ≠ 0 si hay
drift). El release corre el check antes de publicar.

## Entry points (grounding técnico)

- **Precedente a espejar**: `scripts/sync-agent-plugin-skills.mjs` + los scripts root
  `agent-plugin:sync` / `agent-plugin:check`. Mismo patrón: ESM determinístico, `--check` que
  acumula drift y hace `process.exit(1)` con mensaje, notice `<!-- Generated from … do not edit -->`.
- `scripts/sync-npm-readme.mjs` (NUEVO): lee `README.md`, aplica el transform npm-safe, compara/
  escribe `packages/cli/README.md`; soporta `--check`.
- `package.json` (root): agregar `"npm-readme:sync": "node scripts/sync-npm-readme.mjs"` y
  `"npm-readme:check": "node scripts/sync-npm-readme.mjs --check"`.
- `.github/workflows/release.yml`: agregar un step `pnpm npm-readme:check` **antes** de los
  `npm publish` (junto a los "Verify …" existentes), de modo que la release falle ante drift.
- `.github/workflows/ci.yml`: agregar el mismo check en CI (AC-11). Nota: `agent-plugin:check` existe
  pero **no** está cableado en CI hoy; conviene cerrar también ese gap de forma coherente.
- `packages/cli/package.json`: `files` ya incluye `README.md`; decidir en Handoff si se añade
  `prepack`/`prepublishOnly` para regenerar/validar localmente (hoy `prepublishOnly: npm run build`).

  solo apunta a `packages/cli/README.md`.

- **Producto / kaddo.org** (no aplica).

## Scope

1. **Canonical README**: `README.md` como source of truth de la presentación general.
2. **Sync script**: `scripts/sync-npm-readme.mjs` genera `packages/cli/README.md` desde `README.md`,
   reproducible y sin LLM.
3. **npm-safe assets**: `assets/…` → `https://raw.githubusercontent.com/Kaddo-kdd/kaddo/main/assets/…`
   (el banner del cli README ya usa esta forma).
4. **npm-safe links**: links relativos relevantes (`examples/`, `kaddo-power/`, `CONTRIBUTING.md`,
   `assets/`) → URLs a GitHub (`.../tree|blob/main/…`) o kaddo.org; no tocar los ya absolutos.
5. **Content fidelity**: preservar headings, copy, tablas, código, comandos, links y secciones;
   diferencias limitadas a asset URLs, normalización de links y, si es estrictamente necesario, un
   aviso npm.
6. **Generated notice**: `<!-- Generated from /README.md. Do not edit directly. -->` no intrusivo.
7. **Local commands**: `pnpm npm-readme:sync` y `pnpm npm-readme:check`.
8. **Release integration**: `release.yml` sync/check antes de publicar; falla si el README a
   empaquetar no corresponde a la fuente canónica.
9. **Package verification**: `npm pack --dry-run` confirma que `README.md` se incluye en `@kaddo/cli`.
10. **CI drift protection**: `pnpm npm-readme:check` en CI/release que falle cuando el derivado esté
    desactualizado.
11. **Local publish compatibility**: `npm pack`/publish local desde `packages/cli` produce el README
    correcto o advierte/falla (Handoff: `prepack` vs. check sin mutaciones).
12. **MCP README boundary**: `packages/mcp/README.md` no se reemplaza.

## Out of scope

reemplazar kaddo.org; generar contenido con IA; cambiar el versionado; cambiar el mecanismo de
`npm publish`; modificar el README de `@kaddo/mcp` salvo referencias rotas detectadas en validación.

## Validation

- **Root README change**: modificar una sección reconocible en `README.md`, ejecutar
  `pnpm npm-readme:sync` → `packages/cli/README.md` contiene la misma sección actualizada.
- **Drift detection**: modificar `README.md` sin regenerar → `pnpm npm-readme:check` sale con código
  distinto de cero y mensaje claro; tras sync, el check pasa.
- **npm package inspection**: desde `packages/cli`, `npm pack --dry-run` incluye `README.md` con
  contenido actual del README raíz.
- **Asset rendering**: el banner/logo usa una URL válida desde un contexto externo al repo.
- **Relative links**: ejemplos (`examples/`, `CONTRIBUTING.md`, `kaddo-power/`) resuelven a GitHub o
  kaddo.org, no a rutas relativas inválidas dentro del paquete npm.
- **Release pipeline**: tag → release workflow → README check/sync → build → tests → npm publish
  mantiene el pipeline existente.

## Learning

- **El precedente hizo el WI casi mecánico.** `scripts/sync-agent-plugin-skills.mjs` ya definía la
  forma correcta (ESM determinístico, `--check` con exit 1, notice "Generated from…", wired como
  scripts root). `scripts/sync-npm-readme.mjs` lo espeja; el transform real es ~3 regex (asset→raw,
  link relativo→tree/blob, notice). Opción A (archivo generado + versionado + check en CI) encaja
  con ese precedente y hace trivial inspeccionar qué README va al tarball.
- **La Open question de contenido se resolvió mirando, no asumiendo.** El `packages/cli/README.md`
  era más largo (559 vs 304) pero **más stale**: le faltaban Interfaces, Integrations, Operating
  Moments, Adapters, Kaddo Power, Self-hosting. Su extra eran tutoriales verbosos de comandos + un
  Roadmap, contenido que pertenece al sitio de docs (kaddo.org), no a un README de npm. Por eso la
  decisión correcta para el proyecto fue sincronizar el raíz **tal cual**: npm pasa a 306 líneas
  pero gana el overview actual y canónico. No se enriqueció el raíz (habría sido scope creep).
- **La diferencia GitHub↔npm quedó acotada a referencias, no a contenido.** El único delta entre el
  README de GitHub y el de npm son URLs absolutas (assets a raw.githubusercontent, links relativos a
  github.com/tree|blob). No hay segunda versión editorial — exactamente lo que pedía AC-05.
- **La publicación del contenido nuevo ocurre en el próximo release.** Este WI deja
  `packages/cli/README.md` regenerado y commiteado + el guard; la página de npm se actualiza cuando
  se publique el próximo tag `vX.Y.Z` (no es algo que haga este WI directamente).
- **Gap coherente detectado.** `agent-plugin:check` (el precedente) **tampoco** está cableado en CI.
  Cablee `npm-readme:check` en `ci.yml` y `release.yml`; vale un follow-up para hacer lo mismo con
  `agent-plugin:check` y que ambos artifacts generados tengan guard de drift en CI.
