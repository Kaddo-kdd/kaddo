## ¿Por qué Kaddo?

**Tu proyecto ya tiene conocimiento. Solo está disperso.**

En proyectos nuevos, las decisiones desaparecen rápido. En proyectos pre-IA, el contexto
nunca se preparó para los agentes. En proyectos legacy, el conocimiento suele vivir en la
cabeza de las personas. Con IA, esto empeora: los agentes construyen sobre suposiciones
cuando les falta contexto.

Kaddo mantiene el conocimiento mínimo necesario vivo junto al código — sin convertir el
desarrollo en burocracia.

## El modelo de conocimiento

Kaddo organiza el conocimiento en cuatro capas: **Business**, **Product**, **Tech** y
**Delivery**. Cada una alimenta a la siguiente. Los agentes no adivinan — leen contexto
estructurado.

<CardGrid>
  <Card title="Business" icon="document">

  </Card>
  <Card title="Product" icon="list-format">

  </Card>

## El lifecycle de Kaddo

Los Work Items siguen el **Kaddo-native Build Contract** — un ciclo de vida que asegura que
cada cambio es trazable desde la intención hasta la entrega verificada:

<CardGrid>
  <Card title="Captured Intent" icon="pencil">
    Una idea o elemento externo se convierte en un Work Item borrador — `kaddo create` o import desde GitHub Issues, Jira o Azure DevOps.
  </Card>
  <Card title="Refinement → Ready" icon="list-format">
    El work-item-agent enriquece ACs, alcance, módulos afectados. Una persona revisa y marca como ready.
  </Card>
  <Card title="Implementation Handoff" icon="open-book">
    Ensamblaje de contexto agent-agnostic: prompts de deliberación de diseño, instrucciones de implementación, agente y skills recomendados.
  </Card>
  <Card title="Evidence → Verification → Learning" icon="approve-check">
    `kaddo verify` recolecta evidencia, verifica ACs contra release gates y captura aprendizajes para trabajo futuro.
  </Card>
</CardGrid>

Los Work Items se mueven físicamente entre directorios: `draft/` → `ready/` → `in-progress/` →
`completed/`. El lifecycle se aplica por convención — sin lock-in, sin dependencia de plataforma.

## Integraciones

Kaddo se conecta a sistemas de trabajo externos a través de la **Integration Adapter
Foundation**: **discovery** → **import** → **refinement**. Explora elementos externos
(GitHub Issues, Jira, Azure DevOps), importa como borradores de Work Items con confirmación
humana, y luego refina a través del lifecycle estándar. Los secretos permanecen en variables
de entorno y nunca se exponen.

## Knowledge Capsules

Para repos que no puedes mapear como módulos — otros equipos, acceso restringido, contexto solo
de integración — intercambia [**Knowledge Capsules**](/es/knowledge-capsules/): `kaddo capsule
export` comparte un resumen mínimo; `kaddo capsule add` lo importa como *External Knowledge*
en el context pack. Sin mapeo multirepo, sin acceso al código.

## Escala a multirepo

Kaddo modela sistemas distribuidos en muchos repositorios. Desde el repo de arquitectura
mapeas repos secundarios como módulos y mantienes su conocimiento junto al código:

```bash
kaddo modules map        # registra un repo secundario como módulo
kaddo modules list       # lista los módulos mapeados
kaddo add standards|security|stack|git-strategy   # artefactos globales del sistema
```

<CardGrid>
  <Card title="Conocimiento por módulo" icon="document">
    `modules map` genera artefactos `module-design`, `stack`, `security` y `standards`
    bajo `knowledge/tech/modules/<id>/`.
  </Card>
  <Card title="Context module-aware" icon="list-format">
    `kaddo context` y `kaddo explain` muestran los módulos mapeados y su cobertura de artefactos.
  </Card>
  <Card title="Guard de workspace" icon="approve-check">
    El opt-in `kaddo guard --workspace` revisa los repos locales mapeados y señala posible drift.
  </Card>
  <Card title="Artefactos globales" icon="seti:config">
    Estándares, seguridad, stack y estrategia de Git documentan lo transversal una sola vez.
  </Card>
</CardGrid>

## Self-hosting

**Kaddo construye Kaddo con Kaddo.** El proyecto usa su propio lifecycle para gestionar Work
Items, recolectar evidencia, verificar ACs y capturar aprendizajes. El directorio `knowledge/`
contiene el conocimiento de producto propio de Kaddo. Este self-hosting valida el lifecycle de
extremo a extremo y asegura que la fricción interna retroalimenta mejoras.
