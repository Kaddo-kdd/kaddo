## Why Kaddo?

**Your project already has knowledge. It is just scattered.**

In new projects, decisions disappear fast. In pre-AI projects, context was never
prepared for agents. In legacy projects, knowledge often lives in people's heads.
With AI, this gets worse: agents build on assumptions when they lack context.

Kaddo keeps the minimum necessary knowledge alive next to the code — without turning
development into bureaucracy.

## The Knowledge Model

Kaddo organizes knowledge into four layers: **Business**, **Product**, **Tech** and
**Delivery**. Each feeds the next. Agents don't guess — they read structured context.

<CardGrid>
  <Card title="Business" icon="document">
    Problem, users, value proposition, constraints — *why* the project exists.
  </Card>
  <Card title="Product" icon="list-format">
    Capabilities, decisions, quality attributes — *what* the system does.
  </Card>
  <Card title="Tech" icon="setting">
    Architecture, stack, codebase, ADRs, modules — *how* it is built.
  </Card>
  <Card title="Delivery" icon="rocket">
    Roadmap, Work Items, build contract, evidence — *when* and *how well* it ships.
  </Card>
</CardGrid>

## The Kaddo Lifecycle

Work Items follow the **Kaddo-native Build Contract** — a lifecycle that ensures every
change is traceable from intent to verified delivery:

<CardGrid>
  <Card title="Captured Intent" icon="pencil">
    An idea or external item becomes a Work Item draft — `kaddo create` or import from GitHub Issues, Jira or Azure DevOps.
  </Card>
  <Card title="Refinement → Ready" icon="list-format">
    The work-item-agent enriches ACs, scope, affected modules. A human reviews and marks it ready.
  </Card>
  <Card title="Implementation Handoff" icon="open-book">
    Agent-agnostic context assembly: design deliberation prompts, implementation instructions, recommended agent and skills.
  </Card>
  <Card title="Evidence → Verification → Learning" icon="approve-check">
    `kaddo verify` collects evidence, checks ACs against release gates, and captures learnings for future work.
  </Card>
</CardGrid>

Work Items physically move between directories: `draft/` → `ready/` → `in-progress/` →
`completed/`. The lifecycle is enforced by convention — no lock-in, no platform dependency.

## Integrations

Kaddo connects to external work systems through the **Integration Adapter Foundation**:
**discovery** → **import** → **refinement**. Browse external items (GitHub Issues, Jira,
Azure DevOps), import as Work Item drafts with human confirmation, then refine through the
standard lifecycle. Secrets stay in environment variables and are never exposed.

## Knowledge Capsules

For repos you can't map as modules — other teams, restricted access, integration-only context —
exchange [**Knowledge Capsules**](/knowledge-capsules/): `kaddo capsule export` shares a minimal
summary; `kaddo capsule add` imports it as *External Knowledge* in the context pack. No
multirepo mapping, no source access.

## Scale to Multirepo

Kaddo models systems that span many repositories. From the architecture repo you map
secondary repos as modules and keep their knowledge close to the code:

```bash
kaddo modules map        # register a secondary repo as a module
kaddo modules list       # list mapped modules
kaddo add standards|security|stack|git-strategy   # global, system-wide artifacts
```

<CardGrid>
  <Card title="Per-module knowledge" icon="document">

    under `knowledge/tech/modules/<id>/`.
  </Card>
  <Card title="Module-aware context" icon="list-format">

  </Card>
  <Card title="Workspace Guard" icon="approve-check">

## Self-hosting

**Kaddo builds Kaddo with Kaddo.** The project uses its own lifecycle to manage Work Items,
collect evidence, verify ACs and capture learnings. The `knowledge/` directory contains Kaddo's
own product knowledge. This self-hosting validates the lifecycle end-to-end and ensures internal
friction feeds back into improvements.
